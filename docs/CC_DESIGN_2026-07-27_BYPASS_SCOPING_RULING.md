## 0. 裁定
**MGR の提案を採る。閉塞の第一対象は「書き」5箇所。読み15は閉じない（後回しでなく、閉じないと決める）。**

## 1. 基準の訂正【設計:CC-α】
MGR の理由: 「読みは front door を通らなくても**記録を汚さない**」
→ **正しいが、弱い。** より precise な基準はこちら:

> **front door が保証するのは4つ**: ①依頼が記録される ②RRI が分類する ③ゲートを通る ④2DER が routing を決める。
> **直接の「書き」は、この4つ全部を飛ばして台帳にレコードを作る。**
> **＝ 上流に依頼が存在しないレコード＝ orphan が生まれる。**
> **「読み」は何も生まない。orphan にならない。**

**これは [[ai-must-be-internal-actor-not-intruder]] が「orphan 問題の根」と呼んだものそのものである。** 「汚染」ではなく **「上流の無いレコード」** が本体。

## 3. ★閉塞の意味を先に定義する（ここが設計の本体）
**「閉塞」＝直接呼出を削除することではない。** 削除すれば機能が壊れるだけである。

> **閉塞 ＝ その書き込みに対応する「依頼」を front door に通し、書き込みは front door の下流で起きるようにすること。**

- **∴ 各箇所について「その書き込みを起こしている依頼は何か」を先に言語化する必要がある。**
- **言語化できない箇所があるなら、それは「依頼が無いのに書いている」＝設計上の穴であり、閉塞より先に そのことを報告すべきである。**
- **【設計:CC-α】これは実装作業ではなく設計作業である。** 着手時に IMPL に投げるのは「対応する依頼を書き出せ」ではなく、**DESIGN が先に依頼の形を決めてから実装に渡す。**

## 4. 読み15箇所 — **閉じないと決める**
| 理由 |
|---|
| **orphan を生まない**（何も書かない） |
| **内部配線であって入口ではない**。`return_loop.py` は返し経路の内部、`ids.py` は ID 採番、`operator.py`/`dispatch_provenance.py` は観測。**外から入ってくる経路ではない** |
| **読みを閉じても移行の3条件は1つも進まない** |

**「全部塞ぐ」を目的にしない**（MGR の指示に同意）。**閉じない、と決めたことを記録する**——後から「なぜ残っているのか」を再検討する時のために。

### 4-1. ただし1点だけ監査した【監査:CC-α】
**読みが書きの直前にある（読んで判断して書く）なら、読みだけ残すと判断経路が front door の外に残る。**
```
再現: 棚卸し表の file:line を読み、同一ファイル内に「書き」があるかを対応させる
結果: webui.py(読み5+書き1) / build_planner.py(読み1+書き1) / live_worker_runtime.py(読み1+書き1)
      → 書きが対象5箇所に既に含まれているので、判断経路も同時に front door 側へ移る
      operator.py / ids.py / dispatch_provenance.py / return_loop.py は読みのみ＝対応する書きが無い
```
**∴ 読み単独のファイルは、閉じなくてよい。** 上の3ファイルは書きの閉塞に自動的に付いてくる。

## 5. `UNKNOWN` 10箇所 — **`UNKNOWN` のまま。ただし「未解決」として残す**
- **推測で分類しない**（IMPL の判断を支持）。
- **ただし「判定できなかった」ことを台帳に残し続ける。** 放置すると、時間が経つほど「たぶん問題ない」に静かに変わる。**今日 `--check` の感度域を毎回記録させたのと同じ理由。**
