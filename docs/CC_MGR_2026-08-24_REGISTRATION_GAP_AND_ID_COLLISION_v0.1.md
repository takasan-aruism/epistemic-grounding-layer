## 1. ★なぜ落ちたか — 途中で登記簿を切り替えたことに自分で気づいていなかった

- セッション前半: `egl/docs/cc_register.record_doc` を使っていた（8件）
- セッション後半: `twoder/artifact_registry.register` を使っていた（20件）
- **両方に入っていた文書は 0件**

切り替えた自覚が無かった。**どちらか一方にしか無い状態**が17件すべてで起きていた。

## 2. ★★id 空間が衝突している（設計の問題・私では直さない）

```
cc_register.doc_id_for("docs/TAKA_2026-08-23_LEDGER_DETAIL_DESIGN_MEMO_v0.1.md")
   -> ART-948e04d27a
artifact_registry.artifact_id_for("egl", "docs/TAKA_2026-08-23_LEDGER_DETAIL_DESIGN_MEMO_v0.1.md")
   -> ART-948e04d27a
★同じ id
```

**2つの独立した登記簿が、同じ `ART-` の名前空間を、同じ計算規則で使っている。**

### 2.1 これが起こした実害

**私は Taka への報告で「`ART-948e04d27a` に登記した」と8回書いたが、
`artifact_registry` では1件も引けなかった。** id は経路から決定論で計算されるので、
**登記していなくても「それらしい id」が手に入り、報告文だけ見ると正しく見える。**

`twoder/ids.py:resolve` が `ART-` を解決するとき、どちらの登記簿を見るかは1つに決まっている
（＝もう片方に登記した文書は **front door から引けない**）。

### 2.2 CC_REGISTER 側には重複行もある

同じ `doc_id` が複数回 append されている（実測: `ART-e8dfcab57d` が3回、
`ART-84ba0797d0` が3回、`ART-224853a3f3` が2回）。append-only なので消してはいない。

### 2.3 ★裁定が要る（私の権限では決めない）

1. `ART-` を**どちらの登記簿の id とするか**（あるいは片方の接頭辞を分けるか）
2. **両方に登記するのが正なのか**、片方が正で片方は派生なのか
3. 重複行の読み方（最後が効く／全部残す）

**今回は「どちらにも登記する」で揃えた**（Taka「全部登記しないとまずいんじゃない？」に従った）。
これは**衝突を解消していない**。同じ id が2つの台帳に居る状態は残っている。

---

## 3. ★作業そのものが task として投入されていなかった

今回の一連（段0〜段5・chart採用・循環）に対応する **TASK-/ITEM- が1件も無かった**。
`/api/submit` も通していない。∴ **「誰が何のためにこの作業をしたか」を2DER側から引く経路が無く、
私の報告文の中にしか無い状態**だった。「台帳に載らないものは2DERでない」に反する。

**直した**: `ITEM-2DER-EVO-0094`（`PHASE-2DER-EVO-11` / `IN_PROGRESS` / artifact 28件）。
front door `/api/resolve?id=ITEM-2DER-EVO-0094` から引けることを確認済み。

### 3.1 ★ただし task_ids は空のまま

ITEM は立てたが、**この作業に対応する TASK は作っていない**。
理由: 作業は既に終わっており、いま TASK を立てると **DW の state machine に
「これから作る物」として入ってしまう**（実態と合わない）。
∴ **artifact_ids で紐づけ、task_ids は空**にした。これが正しいかは**未確認**。

## 5. ★この事故から取るべき手当て

「登記したつもり」を防ぐには、**id を計算した時点ではなく、引けた時点で報告する**必要がある。
今回は `AR.resolve(aid)` / front door `/api/resolve` で**引けることを確認してから**報告した。
