## 第1章 入口は一つ（規律1）

**正式入口は webui の front door だけ。**

| 経路 | task を作る | task を進める | 実行記録(TRACE) | 分類 |
|---|---|---|---|---|
| `POST /api/submit`（webui） | できる | **できる** | **残る**（`webui.py:541,543` が唯一の書き手） | **CANONICAL** |
| `GET /command`（UI） | 同上 | 同上 | 同上 | **CANONICAL** |
| `python3 -m twoder.submit` | できる | **できない** | **★1件も残らない**（`G-36`） | **BYPASS_UNAUTHORIZED** |
| python 直叩き / モジュール import | — | — | — | **BYPASS_UNAUTHORIZED** |

- **接続**: `http://100.107.6.119:8770`（**tailscale bind。localhost では繋がらない**）／Basic 認証 user=`taka`・token=`/home/takasan/twoder/.access_token`
- **run-gate は webui プロセス内の変数**。**再起動すると「まだ何も投入されていない」に戻る**。既存 task を進めるには同一依頼文を再投入して gate を立て直す（task id は依頼文の sha1 なので task は増えない）。**再投入した回数と理由を必ず書く。**
- **契約検査**: `immutable_tests` に `def test_` 行が1件も無い依頼文は `ValueError` で弾かれる。**これは欠陥ではない。契約が欠陥品なので弾かれるのが正しい。**
- **投入の作法**: 依頼文を1文字も変えない／通りやすくする書き換えをしない／1回だけ投入する（再投入は「再投入した」と書く）／**投入前に予想を書き、外れたら「外れた」と書く。**
- **CLI を使うなら、使う前に「この投入は実行記録を残さない」と書く。** 書かずに使わない。
- **★投入は `/api/resolve` で読み返して初めて「書けた」と言う（v1.6）。** **`progress_write.ok` だけを証拠にしない。**
  - **根拠（2026-08-02・同日2件）**: front door の submit が**時間切れで黙って消える**（`http=000`）。**応答が返らなかった投入は「書けていない」ではなく「不明」**であり、**読み返すまで再投入しない**（二重書き込みを作らないため）。
  - **v0.3 §11.3（同種失敗2回で運転規則を修正する）に従い、機能でなく規則で塞いだ。管理対象は増やしていない。**
  - **畳む条件**: 投入の応答が「書けた／書けていない」を決定論で返すようになった時（`http=000` が起きない、または front door 側が読み返しを内包した時）。

## 第2章 production コードを Claude が直接書かない（規律2）

- **実装は 2DER の worker が出す。Claude は検査して配置する役だけ。**
- **worker の隔離は「書けない」ではなく「書かない」**（`G-90`・2026-07-31 訂正）。実際に効いているのは3つ: ①呼び手が `tempfile.mkdtemp(prefix="refora_")` を渡す（`webui.py:268`）／②planner が production 配下の `target_workspace` を弾く（`build_planner.py:59,293`）／③`AUTO_COMMIT_FORBIDDEN` を assert で守り runtime は `git commit` しない（`live_worker_runtime.py:204`）。
  **効いていない**: `validate_sandbox` は設定辞書に `True` と書いてあるかを見るだけで OS 隔離ではない。**∴「安全だから押してよい」と読まない。「いまの呼び方なら入らない。呼び方が変わったら測り直す」である。**
- **成果物は `tempfile.mkdtemp()` 配下に出て消える。受け取りは同じ作業の中で完了させる。** 失われたら「失われた」と記録し、黙って再投入しない。
- **配置の作法**: 検査してから置く／`artifact_registry.register` + `record_change` に記録が残る場合に限り置く（**記録の無い配置＝「いつの間にか在るファイル」は禁止**）／置く者と検査する者を分ける／**run-gate を回避しない。**
- **sandbox は本番モジュールを import できない。** 依頼には必要な関数を引数で受け取る薄いアダプタ仕様を渡す。渡さなければ worker は在りもしない API を想像で埋める。

### 2-1. ★進化単位を立てる時に「worker に出せる核」を先に決める（v1.8）

**投入前に、その単位に *純関数として切り出せる核* が在るかを決める。無ければ「★この単位の 2DER 工程は 0 である」と★宣言してから始める。宣言せずに始めない。**

- **核の条件**: ①入出力が値で閉じる ②本番モジュールの `import` が要らない ③封印試験が書ける。
- **根拠（2026-08-03・実測）**: 段4 の3単位（`EVO-0036` / `EVO-0051` / `EVO-0049`）で **2DER 担当工程が連続 0**（台帳の `actor=` は MGR と Claude のみ）→ **v0.3 §12.1 発動**。
  設計が実行事実だけで特定した閉塞は **「能力が無い」ではなく「呼べる形にしていない」**——**成果物が本番 repo の1〜2行の配線である限り、契約（骨格＋封印試験）の形にならず worker に出せない。**
  **対照**: 2DER が唯一 実作業を担えた S-3 の成果物は **純関数（`human_view.py` 70行・sha256 で無改変を確認）** で、Claude が書いたのは **配線28行だけ**だった。以後の3単位は純関数の塊が0で、全て配線だった。
- **∴ これは能力の問題ではなく作業の切り出しの問題**であり、**新能力の追加では閉じない。**
- **効能**: 「やってみたら 0 だった」を **「0 だと知って始めた」** に変える。**自己申告の格上げ（v0.3 §13.3）と同じ病を、着手側で止める。**
- **畳む条件**: 2DER 担当工程が実案件で連続2単位 1 以上になった時。

### 2-2. ★封印試験の fixture は実データから採る（v1.9）

**★作った文字列で通した試験は、通っても通ったことにならない。★依頼文に書いた制約は、★試験でも縛る**（第11-2 の #7 の具体化）。

- **根拠（2026-08-03・同型2回）**: `EVO-0052` の封印試験4本目の fixture が `"note=next=MGR x"`（**先頭が `note=` で始まる非現実的な文字列**）だったため通ったが、**実物は** `"actor=MGR stage=… note=next=IMPL …"` で**先頭が `actor=`** ∴ **実データでは取れなかった**。1度目＝S-3 で試験が書式を検査していなかった件。
- **もう一方の欠け**: 依頼文に「`DESIGN/IMPL/MGR/TAKA/NONE` のいずれかの時だけ」と書きながら**試験で縛らなかった**ため、`next=FOO` が素通りした。
- **★値を列挙したら、試験は★対で置く（v1.10）**: ①**列挙した値が★全部 通ること** ②**列挙外が★弾かれること**。**片方だけでは通らない。**
  - **根拠（2026-08-03・同型3回目・★前回と裏返し）**: v1.9 を足した後、設計は**否定側（`FOO` を弾く）だけ**を置き、**肯定側（5語すべてが通る）を1本も置かなかった**。結果、成果物の許容集合が **`{IMPL,DESIGN,MGR,NONE,ETR}`＝`TAKA` が欠け `ETR` が紛れ込んだ**まま **9本 全通**した。
  - **実害の形**: いま `TAKA` の手番が台帳に無いので表面化しない。**Taka の手番を書いた瞬間に静かに落ちる。**
- **★★依頼文に文面や値を書くなら、試験で縛る。★縛らないなら、★書かない（v1.11）。**
  - **これは規則を増やす方向ではなく、★減らす方向**——**書かなくてよい物を書かない**という逃げ道を先に用意する（規律9）。
  - **根拠（2026-08-03〜04・★同型5回）**: ①fixture が実データの形でなかった ②列挙の肯定側を書かなかった ③手順書に許容語（`PASS`/`FAIL`）を書かなかった ④`NOT_RUNNABLE` の理由文を1本も縛らなかった ⑤`BLOCKED`/`TASK_MISMATCH` の文面を指定しながら試験で縛らず、**成果物が別の文面で通った**。
  - **★v1.9 と v1.10 を足しても再発した**＝「書いたことを試験しろ」だけでは足りない。**「試験しないなら書くな」を対で置く。**
  - **★1つの `assert` に2つの意図を入れない**（④は `or` で繋いだため、片方が空でも通った）。
  - **畳む条件**: 依頼文の記述と封印試験の対応を機械が確かめられるようになった時。
- **★★fixture の癖に合わせられていないかを、★癖を振って確かめる（v1.12・★v1.9 の対）。**
  - **作法**: 同じ入力から **癖を足した版と外した版**を作り、**結果が変わらないこと**を試験で縛る。**変われば癖に合わせている。**
  - **根拠（2026-08-04・★v1.9 が裏目に出た初めての実例）**: `EVO-0049` 段0 の成果物は **封印試験11本を全通**したが、実体は逐語 `if "★" in segment: kind = "BULLET"` ——**`★` の有無だけで箇条書きを判定**していた。**`★` は依頼文に1度も出てこない**。出てくるのは**実データから採った fixture の中だけ**（我々の台帳 note が `★` で埋まっているため）。
  - **実演**: `★` を含まない箇条書き `- 一つ目\n- 二つ目` → **BULLET が0件**。**試験は通り、実データで落ちる。**
  - **∴ v1.9（実データから採れ）は正しいが、★実データには癖が在る。** 癖を振らないと、**癖に合わせた実装が全通する。**
  - **これは Taka の「邪魔な自由度を振って、動かないものだけを結論にする」の適用。規則は増やさない——v1.9 の対として置く。**
  - **畳む条件**: fixture の癖の候補を機械が列挙できるようになった時。
- **★★依頼文に規則を列挙したら、★規則1つにつき試験1本を対応させ、★対応表を SPEC に書く（v1.13・★v1.11 の具体化）。**
  - **形**: 「規則① → `test_xxx`」を**表で書く**。**機械が数えられる形**にする（規則の数 ≧ 対応した試験の数、で不足が出る）。
  - **根拠（2026-08-04・★同じ1件で3回）**: `EVO-0049` 段0 で ①規則②（箇条書き）を縛らず **`★` 依存が全通** ②依頼文から2文が落ち **本体が空** ③規則③（句点→`SENTENCE`）を縛らず **句点で一度も割らない**成果物が **13本 全通**した。
  - **v1.11 は「書いたら縛れ」だが、★どれを縛ったかを数えられない。** 3つの規則のうち **1つだけ試験が無い**状態が、**2回続けて素通り**した。
  - **副次**: 陽性対照の失敗（2用件を1文に詰めた実物が割れない）は、**規則③の欠落がそのまま出たもの**。**対照が規則の欠落を指した**のは良い形。
  - **畳む条件**: 規則と試験の対応を機械が数えられるようになった時（★SPEC の表を機械が読む）。
- **∴ 直すのは契約（試験）であって成果物ではない。** worker は試験どおりに実装しており落ち度は無い——**契約が欠陥品なら、通ることが欠陥である**（第1章と同じ思想）。
- **作法**: fixture は **front door から実際に取れた文字列を貼る**。貼れないなら「貼れなかった」と書く。
- **畳む条件**: fixture が実データ由来であることを機械が確かめられるようになった時。

## 第3章 記録は台帳へ。.md は「台帳へ書けなかった時」だけ（規律3）

- **進捗・状態・判断は台帳に書く。** `.md` は、**台帳に書く口が無いために書けなかった記録**に限る。**その .md には「どの口が無いから .md なのか」を1行書く**（それが次に作る口の名前になる）。
- **台帳を直接読まない**（`cat`/`grep`/`Read`/`open`）。**フックが拒否する。** どうしても必要なら `【直読】` と明記し理由を書く。**回数が「読み出し機能が足りない」ことの数字になる。**
- **読み出しの口は在って動く**: `GET /api/resolve?id=<ID>` — `TASK-` / `DE-` / `ITEM-` / `ROADMAP-` の解決を実測（2026-07-31・4/4）。`resolved` が true/false で決定論に返る。`read_only: true`。
- **全体像の口**: `GET /api/roadmap` / `GET /api/control`（ROADMAP_REGISTRY: 15フェーズ・86項目・depends_on・authority・evidence_de_ids）。
  **★現状の欠陥（未修正・C-4）**: 両者が同じ台帳を違う数で答える（DONE 65 vs 67／フェーズ 11 vs 15）。**どちらかを正典にするまで、この2つの数字を根拠に使わない。**
- **読んでよいもの＝コードの構造**（どの関数がどこから呼ばれるか。それは実装作業そのもの）。**読んではいけないもの＝台帳の中身。**
- **新しい台帳・新しい `*.jsonl` を作らない。**「小さいから」「一時的だから」も禁止。**畳めないものを使い続けるときは、畳む条件と、いま何が足りないかを必ず併記する。**

## 第4章 文書を増やさない（規律4）

- **一つの進化単位に説明文書を作らない**（v0.3 §3.4）。記録は既存の正典・状況表・run artifact へ追記する。
- **新規文書が許されるのは4条件すべてを満たす時だけ**: ①既存正典に格納不能 ②実行または移管に必要な契約を定義する ③作成者・利用者・廃止条件が明確 ④**その文書が廃止する既存文書を名指しできる**。
- **廃止は「削除」ではなく「置換」**（Taka 条件）。旧文書は消さず、**旧文書 → 新正典のどの章 → Deprecated** の対応表を残す（§12）。**これを残さないと、古い commit を読んだ次の Claude が旧文書を掘り返す。**
- **往復のたびに文書を書かない。** 予想の範囲で返ってきたものは進める。**裁定が要るときだけ書く。**
- **★1つの進化単位に残す .md は ★2種類だけ（v1.3 追加・Taka 指示 逐語:「★1件に14本は多い。どうせ読まんだろ。★仕様と実測だけ残して、★往復の説明は書くな」）**
  - **残す**: ① **BUILD SPEC**（仕様・実装源） ② **実測**（数値・逐語・受入の当否）
  - **書かない**: 訂正・受領・経緯・自己申告・「私の前提が崩れた」の類。**★台帳の `status_note` に1行で書く。**
  - **実測（2026-08-02）**: `EVO-0031` 1件に `.md` が **★14本**。うち仕様2本・BUILT 2本で、**残り10本は往復の説明**だった。
  - **上限**: **1件につき .md は ★4本まで**（仕様2 + 実測2 を目安）。**超えるなら、超えたと書いて止まる。**
  - **★暫定の運用（v1.5・2026-08-02・Taka 指示「一応 現状 簡単にできる管理方法を採用し、本格的なところは台帳が完成してから」）**
    - **実測は .md にしない。★台帳の `status_note` に書く**（実証済: 数百〜千字は入る）。
    - **.md に残してよいのは ★BUILD SPEC（実装源）だけ。★1件につき1本。**
    - **.md を置いたら、その ITEM の note に ★`spec=<ファイル名>` を1行 書く**（★台帳から辿れない .md を作らない）。
    - **手番は note の先頭に ★`next=MGR|DESIGN|IMPL|TAKA|NONE`**（`ITEM-2DER-EVO-0046`）。
  - **★`DONE` / `DROPPED` の item に記録を足すときは、`status` に★現在の値をそのまま書く（v1.7）。判定を変えてよいのは MGR だけ。**
    - **根拠（2026-08-03・同日2回・別の役が1回ずつ）**: 実装が数字の訂正を（03:51）、設計が受領を（03:56）書いた際、`status: IN_PROGRESS` を添えたため **MGR が出した `DONE` 判定が静かに巻き戻った**。**人ではなく仕組みの問題**（`progress_seal` の必須欄に `status` が在り、**記録だけを足せない**）。
    - **静かに戻るのが厄介**＝気づいたのは状況表の件数。**書く前に、その item がいま `DONE` かどうかを `/api/resolve` で見る。**
    - **v0.3 §11.3（同種2回で運転規則を直す）に従い、機構より先に規則で塞いだ。管理対象は増やしていない。**
    - **畳む条件**: `status` を省いて記録だけ足せる口ができた時（`ITEM-2DER-EVO-0052`）。
    - **★畳む条件**: **台帳の再構成（段4）が完了し、長文を勘定科目で明細化して台帳へ入れられるようになった時**（`ITEM-2DER-EVO-0047`）。**それまでは .md を1本だけ残す。**

## 第5章 原因が確定した小さな配線不良は、裁定より先にパッチ（規律5）

**v0.3 §12.6（調査過剰停止）の現場版。**
- **原因位置が確定し／変更が小さく／可逆で／テスト可能** なら、**説明文書・裁定文書より先にパッチと実行を出す。**
- 逆に、**原因が未確定なまま実装しない。**
- **禁止する順序**: 説明文書 → 評価文書 → 裁定文書 → 新計器 → 実装待ち。
- **例（2026-07-31 に破った）**: PLAN 成功後に gate が閉じる件は3行で原因が確定していたのに、調査と裁定へ回した。

## 第6章 計器は機械が出す値だけ（規律6）

- **人が値を入れる計器は独立証拠にしない**（v0.3 §3.5・§13.3）。**補助表示としてのみ可**で、その旨を表示に書く。
- 計器には必ず持たせる: **入力元 / 算出規則 / 停止閾値 / 廃止条件 / 既存計器との重複確認**。
- **計器が自分を数えないようにする**（短い名前を使わない／自分と先祖を除外／0 でない値はまず自分を疑う）。
- **状態を変える呼び出しの応答を捨てない**（`-o /dev/null` にしない。捨てた瞬間に「やっていない」と誤報する）。

## 第7章 「在る」と「動く」を分ける（規律7）

- **「ソースに在る」を「動く」と書かない。** 動作を主張するなら**実行した再現コマンドと結果を併記**する。
- **「無い」と書くときは探索範囲を明示し、叩いて確かめる。** **「存在しない」ことを示す走査に `head` / `limit` / `-m` を付けない**（数えてから中身を見る）。
- **監査結果には総件数・確認件数・打ち切り有無を必ず書く。**
- **1回の観測で断定しない。** 揺れうるものは回数と分布で書く。
- **未確認は `【未確認】`** と書き、同じ行に「いつ・誰が」を書く。
- **「置いた」なら「どこから読めるか」まで書く。** 読む口が無い置き物は成果にしない（v0.3 §15）。
- **★逆も書く（v1.1 追加）: 「読める」なら「どこから書けるか」まで確かめる。** **読み手だけ在って書き手が無い形を、機能が在ると読まない。**
  - **根拠（2026-08-01・1日で4回）**: ①`roadmap_registry.set_status` は在るが front door から呼べなかった（C-1）／②`JUDGE_REQUIRED` は状態としては在るが `ingest` に受け手が無い（`EVO-0029`）／③`BLOCK` の読み手は `workcell.py:185-186` に在るが `record_*` 7つに書く関数が0件（`EVO-0028` の滞留6件が畳めない理由）／④`next_information_need` は投入時に書かれるが停止時に更新されない。
  - **∴ v0.3 §11.3（同種失敗が2回で運転規則の修正候補を出す）に従い、規則側で塞ぐ。** **新しい機能を提案するときは、読む口と書く口を対で名指しする。片方しか書けないなら「片方しか無い」と書く。**
- **作業ディレクトリに依存するコマンドは絶対パスか明示 cd で始める**（`/home/takasan/twoder` には標準ライブラリを隠す `operator.py` が在る）。

## 第8章 測定は 2DER の中で回す（規律8）

- **2DER の外で回した実験・測定は実績に数えない**（2026-07-31: LLM 130本が全部 外だった）。
- 外で回すなら、**「これは 2DER の外である」と書き、移管予定を1行書く。書けないならやらない。**
- **測定の LLM 呼び出しは並列で回す**（直列で3時間半を溶かした実例あり）。
- **対照を取る／母数を記録する／元データを残す／最低 10 run × 2 batch**（1バッチの揺れを効果と読んだ実例あり）。

## 第9章 一つ進めるために二つ増やさない（規律9・Taka 追加）

> **一つの閉塞を解消するために、新しい管理対象を二つ以上増やしてはならない。**

- 管理対象＝**文書 / 計器 / 役割 / インスタンス / 承認工程 / 台帳**。
- **増やすなら、その場で「既存の何を廃止するか」を同時に書く。** 書けないなら増やさない。
- 根拠（2026-07-31 の実物）: 問題 → 説明文書 → 測定 → 計器 → 新ルール → 新担当 → **本線は進まない**。
- v0.3 の「進化価値 − 維持コスト」と同じ思想。**NEUTRAL は未完了、NEGATIVE は失敗。**

## 第10章 役割・経路・報告・commit（畳んだ最小版）

**経路（例外なし）**: `MGR ──(宛: 設計/監査のみ)──► CC-α ──► IMPL ──(BUILT)──► CC-α(監査) ──► MGR ──► Taka`

| | やること | やらないこと |
|---|---|---|
| **MGR**（管理） | 基本設計・優先順位 / 裁定 / Taka への報告 / commit・push / 計器の維持 | 実装しない。コードを読んで欠陥を特定しない。数字を自分で出さない。実装へ直接指示しない |
| **CC-α**（設計/監査） | 基本設計を BUILD SPEC に落とす / 独立監査 / 設計裁定 | 実装しない。自分の監査を自分で承認しない |
| **IMPL**（実装） | 実装源1本から作る / 測定を回す / BUILT を返す | 設計判断をしない。判定基準を作らない。commit しない |

- **Taka へ上げてよい4類型**: ①目的・優先順位そのもの ②対外的・不可逆な行為 ③Taka の資源（時間・金・repo 履歴）を使うもの ④我々の判断が割れて根拠で決着しないもの。**「念のため確認」を禁じる。上げる前に「これは調べれば分かることか」を確かめる。**
- **報告トリガー**: 段の完了 / gate RED / 裁定待ち / 問われた時。**小さな commit をダラダラ書かない。**
- **報告の書き方**: **平易な言葉＋具体例。専門用語を並べない。** 通常報告は v0.3 §18 の形式に限る。
- **MGR が「Taka がこう言った」と書いた文書は一次典拠**（【伝聞】として着手を止めない）。代わりに MGR は**逐語引用する／拡大解釈しない／誤伝は自責で訂正**。
- **commit / push は MGR のみ。5 repo を個別に commit + push し、全 repo の ahead/behind を検証する**（`ds`/`rri`/`egl`=main、`dev-workcell`/`twoder`=master）。**commit は保存であって承認ではない**（未監査なら「未監査」と明記）。
- **相手に届けるものは必ず新しい名前で置く。既存文書を同名で差し替えない**（差し替えて5時間 沈黙した実例あり）。
