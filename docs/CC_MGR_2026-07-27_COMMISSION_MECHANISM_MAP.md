## 2. D-17 — 作るもの: `egl/docs/2DER_MECHANISM_MAP.md`（常設・日付なし）
**次の4つを、それぞれ「入口 → 通る段 → 記録先 → 誰が動かすか」で書くこと。**

| # | 章 | 含めること |
|---|---|---|
| **1** | **接続（どうやって入るか）** | 入口の全列挙（CLI / webui / 直叩き）。**各入口が何をでき、何をできないか**（CLI は task を作れるが進められない 等）。**auth の要否。** |
| **2** | **記帳（どうやって書かれるか）** | `submit()` が通る段を順に。**各段が何を記録し、どの台帳に書くか。** DE / artifact / DW event / 発話記録それぞれの**書き手の関数名**。**誰が書けて、誰が書けないか**（worker は production repo に書けない 等）。 |
| **3** | **参照（どうやって読まれるか）** | `ids.py::resolve` の接頭辞と持ち主の対応表。**★front door から到達できるか／できないかを、いま在るとおりに書く。** |
| **4** | **進行（誰が動かすか）** | `dispatch_once` / `run_until_barrier` を呼ぶのは誰か。**PLAN の actor が Qwen になる条件と、ならない条件（fail-closed）。** |

### 2-1. ★書き方の規律（これが「健忘しても不変」を担保する）
1. **各行に再現手順を付ける**（`grep` / 実行コマンド）。**読んだだけか、動かしたかを区別する**（運用方針 §3-6）。
2. **【未確認】を消さない。** 確かめていないものは確かめていないと書く。
3. **「無い」を書く。** 例: **front door から台帳を読む経路は無い。** ——**これが最も重要な行である。**
4. **散文で説明しない。表と経路で書く。** **散文は記録ではない**（§6-2）。
5. **account chart は触らない。** 勘定科目は**埋め込みで自由に作られ、版上げに Taka 承認が要る**（本日確認済）——**その決まり方も §2 に含めること。**
