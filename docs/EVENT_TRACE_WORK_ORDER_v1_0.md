## 1. 本文（★Taka 逐語）

以下の方向性なら、これまでの議論とも整合すると思います。

まず「RRIの全機能を実装する」のではなく、全処理の履歴を強制的に残す基盤を先に完成させます。これにより、後からRRIの機能を追加・変更しても、実際に何が起きたかを追跡できるようになります。

### 指示書 — RRI処理履歴(Event Trace)基盤の実装

**背景**

現在、RRIは設計上多くの役割を持つが、実際に何が実行され、何が実行されていないかを後から確認することが難しい。
今後RRIの機能追加を進める前に、処理そのものを証拠として残す仕組みを優先する。
これはRRIを完成させる作業ではない。
RRI・EGL・DW・Ledgerを含む全処理を一本の流れとして観測可能にするための基盤整備である。

**目的**

一本の依頼について、
* 何を受け取り
* 何を判断し
* 何を生成し
* 次にどこへ渡したか
を、後から100%追跡できるようにする。
推測ではなく、実際に実行された履歴を証拠として残すことを目的とする。

**基本方針**

RRIの仕様を先に固定しない。
代わりに、**処理が発生したら必ずイベントを記録する。**
これを唯一のルールとする。

**記録対象**

RRI内部だけではなく、DS / RRI / EGL / DW / Ledger / その他Worker を含め、処理単位でイベントを記録する。

**最低限保存する項目**

* Event ID
* 親Event ID
* Session ID
* Request ID
* Timestamp
* Component名
* Function名
* 入力
* 出力
* 次に渡した先
* 実行結果
* Error有無

**LLM処理の場合は追加**

* 使用モデル
* Prompt種別
* 構造化前データ
* 構造化後データ
* 信頼度
* 不足情報
* 採用した候補
* 却下した候補（取得可能なら）

※巨大なChain of Thought等は保存対象としない。

**重要**

処理結果だけではなく、**処理を実行した事実**を残す。

例
* request_typeを実行した
* intent_strategyを実行した
* select_strategyは呼ばれなかった
* context_bindingはスキップされた

これらもイベントとして残す。

**Eventの例**

Request受信 → request_type → context_binding → intent_strategy → research_intent → EGL登録 → DW投入 → 完了
この一連を一本の系列として追跡可能にする。

**実装上の注意**

このイベント記録は、RRIのロジックを書き換えるためのものではない。
既存処理へ最小限のHookを追加し、処理開始・終了を記録する方式を優先する。

**禁止事項**

今回の作業では、
* 新しいRRIロジックを追加しない
* 4軸アルゴリズムを書き換えない
* 7戦略を書き換えない
* EGL仕様を書き換えない
* DW仕様を書き換えない

目的は挙動の変更ではなく、**実際に何が起きたかを観測可能にすること**である。

**完了条件**

以下が実測で確認できること。
* 一つのRequestについて、DSからDWまでの処理履歴が一本で追える。
* 各イベントについて、入力・出力・次の処理先が確認できる。
* **呼ばれなかった処理も識別できる。**
* Event IDを辿るだけで、一本の依頼が最後まで追跡できる。
* 「推測」ではなく、イベント履歴のみでRRIの実行経路を説明できる。

**この作業の位置付け**

これはRRI完成ではない。
RRIを今後安全に拡張するための観測基盤である。
以後の機能追加・仕様変更・4軸実装・7戦略改善・EGL連携・DW連携については、本基盤により「実際に何が変わったか」を実測で比較できる状態を作ることを目的とする。

この方針なら、以前から話している「Execution Architecture」「EGL」「帳票（Ledger）」とも矛盾しません。むしろ、それらを一本の実行履歴として結び付ける土台になります。RRIの責務が今後具体化しても、このイベント基盤はそのまま再利用できます。
