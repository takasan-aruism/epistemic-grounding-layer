## 1. 問題認識
現在の2DERは、一本の経路が端まで通れば大きな前進になる段階にある。一方で、その一本が「本来必要な検証面を十分に通った結果」なのか、単に今回の条件で偶然通ったのかを事前に保証する設計はまだ弱い。失敗型の蓄積や self_check は改善しているが、これは主として既知の失敗を再発させないための前段であり、「そもそも何を、どこまで設計・調査・試験すべきか」という母数の生成とは別問題である。
本来の実装段階では、失敗を発見してから直すことを主工程にしてはならない。建築に例えれば、着工前に地盤・構造・材料・施工条件を確認し、想定可能なリスクを設計と試験へ展開したうえで施工するべきである。

## 2. 基本思想
見積もる対象は「トークン数」そのものではなく、成立させるために必要な作業面・検証面の母数である。設計を先に構造化し、その設計から必要作業・影響範囲・試験面を展開する。計算資源は後段で割り当てる。単位が100でも1000でもよく、過去実績から換算係数を育てる。LLMの専門家感覚に依存せず、台帳・経路表・機能表・RRI・失敗履歴・実測値を根拠にする。「通った＝健全」を禁止し、予定した検証母数に対する実施率と結果で健全性を扱う。

## 3. 想定する全体工程
要求 → 要求の構造化 → 選択肢生成 → 人/上位判断による選択 → 設計確定 → 作業母数生成 → 検証母数生成 → 資源見積もり → 実行計画 → 実装 → 予定試験 → 完了判定
例: 「WEBページを作りたい」という曖昧な要求を即実装へ送らず、用途・利用者・優先事項・デザイン候補・必要機能・既存接続・試験条件を先に明細化する。価値判断が必要な A/B/C の選択のみ人へ返し、選択後は2DERが必要作業と検証面を展開する。

## 5. Work Unit（仮称）
最初から正確な時間やトークンを予言する必要はない。設計から展開された作業単位を仮の Work Unit として数え、実行後に実コストを対応付ける。
例: 調査1件、契約1件、変更1箇所、経路確認1本、正常試験1件、異常試験1件、環境確認1件などを別種の単位として記録する。単純加算にする必要はなく、種別ごとの重みは実績から更新する。
重要なのは「100WUなら重い」という固定値ではなく、同じ型の仕事について予測WUと実測資源が継続的に対応付くことである。

## 6. 計算資源として先行計測する項目
LLMごとの入力/出力 token 数／Worker・Claude -p・Qwen 等の呼出回数／retry・差戻し・再設計回数／機械試験数・LLM監査数・上級監査数／変更ファイル数・変更箇所数／経路表上で触れた区間数／RRI調査件数・未知→既知になった件数／実経過時間と待機時間／失敗型の発生数と既知・未知の別／OS・ドライバ・ディレクトリ・権限・ハードウェア等の環境確認面。
現段階ではこれらを評価や停止条件へ直結させず、将来の見積もり係数を作るための実績として蓄積する。既存台帳で保持可能なら新台帳を作らない。

## 7. 環境・基盤を見積もり対象から外さない
Workstation、OS、ディレクトリ構成、ドライバ、GPU/CPU/RAM、権限、常駐サービス、依存パッケージ等について、現在RRIや既存機能がどこまで把握・検査しているかを先に棚卸しする。「コードだけを試験して環境を未確認」の状態では、設計母数そのものが欠ける。既存機能を調査し、重複実装は避ける。

## 8. 導入時期
本実装は、経路表・機能表が十分に整い、設計自動化へ入る時点を基本とする。順序は以下を暫定正とする。
経路表 → 機能表 → 設計自動化 → 作業量/検証量見積もり → 計算資源割当 → 実装
ただし実績計測だけは先行してよい。現在の開発を止めて巨大な見積もりシステムを作ることは禁止する。

## 9. 将来の完了判定の方向
将来は「一本通った」ではなく、設計時に生成した母数に対して、調査・実装・検証がどこまで消化されたかを完了判定に使う。未知の検証面が残る場合は COMPLETE ではなく、未検証の住所と理由を残す。これにより「ラッキーで通った」を健全性の根拠にしない。

## 10. 実装時の禁止事項
見積もり機能だけを独立した巨大システムとして横に増設しない。LLMに「この作業は何時間？」と自由推定させ、その値を証拠にしない。既存のRRI・台帳・経路表・機能表・self_check・failure memory と重複する器を作らない。現時点の不完全な母数を精密な数値に見せない。既知の成功例だけから試験範囲を決めない。出てはいけない結果・境界・環境条件も母数に含める。

## 11. 次回再開時の最初の調査
設計自動化に着手する際、最初に新機能を実装せず、既存2DER/RRIに存在する「計算資源」「環境認識」「試験設計」「作業量」「未知項目」「機能明細」の機能と記録を実測で棚卸しする。その結果を経路表・機能表へ対応付け、不足分だけを設計する。

**要約**: 2DERの次段階では、実装を自動化する前に「何をやれば実装完了と呼べるか」を機械が展開できる必要がある。見積もりとは、その母数を作り、実績から必要資源へ換算する機能である。

## 12. v0.2 で追加する Domain Design Engine
Domain Design Engine は、Domain Manager が案件を設計するときに使う共通機構である。Domain Manager 自身が失敗履歴・成功履歴・経路・環境・外部情報をすべて調査する構成にはしない。Manager は案件を分類し、必要な専門 Worker を選択して並列に起動し、返却結果を統合して Domain 設計、Contract 群、Work Unit、検証母数へ落とす。
役割概念は Domain Manager Design、実行機能は Domain Design Engine、利用主体は各 Domain Manager とする。したがって DW / 経路表 / RRI 等の Domain と横並びに新しい Domain Manager を一つ増やすことを目的としない。

## 13. 必須材料を決める原則
第一原則は「答えは過去にある」である。案件ごとに LLM がゼロから必要材料を考えるのではなく、まず既存の勘定科目、台帳、過去の成功・失敗、経路表、機能表、RRI、既存 Contract、実測記録から、同型案件で必要だった材料集合を引く。過去に一度確定した設計判断は、次回から自由設計ではなく参照へ落とす。
既存の勘定科目・台帳に答えがない場合だけ未知処理へ進む。未知処理では最初から一案へ収束させず、必要材料、調査方法、分類候補、不足理由、代替経路を広く列挙する。その後、既存台帳との重複、証拠、実行可能性、影響、コスト等で絞る。採用・実証された結果は勘定科目・台帳へ戻し、次回から既知として再利用する。
この循環により、Domain Design Engine は使用するほど LLM の自由判断領域を縮小し、既知案件を機械的参照へ移していく。

## 14. 専門 Worker の役割
（★原文は表）External Research Worker は最後の手段とし、内部に存在する情報を外部検索で置き換えない。Environment Worker は優先度を低めにし、環境変更を伴う案件や内部材料だけでは説明できない案件で起動する。

## 15. 並列実行
専門 Worker は相互依存がない範囲で原則並列に処理する。Domain Manager は全 Worker の完了を待って逐次調査するのではなく、勘定科目と案件特性から必要 Worker 集合を先に決め、同時に起動する。
並列化の目的は速度だけではない。失敗側・成功側・経路側などを独立に引くことで、一つの主体の見落としや自己一致を減らし、結果を相互検算できるようにする。

## 16. Domain Manager と Worker の責務境界
Domain Manager は検索エンジンにならない。担当するのは、(1)案件の勘定科目分類、(2)必須材料集合と必要 Worker の決定、(3)Worker の起動、(4)結果の統合、(5)不足・衝突・未知の判定、(6)Domain 設計・Contract 群・Work Unit への変換である。
Worker は担当範囲の材料を取得・検査し、出所、母数、取得数、未取得数を伴って結果を返す。Manager は Worker が返した生の調査を再実施しない。独立検算が必要な場合は別 Worker / 別主体へ依頼する。

## 17. 材料完全性と『0件』の扱い
2026-08-17 の実測では、materials_used が「渡された材料」しか表示しないため、渡し忘れた relay_chain が計器上から完全に消えた。さらに当該値が 0 件だったため、欠落していても結果件数が変化せず、「不在が遵守に見える」状態が発生した。
したがって、分母・取得数・未取得数の表示だけでは十分ではない。処理開始前に『この勘定科目・案件で本来必要な材料集合』を required materials として確定し、required の一つでも欠ければ missing_material として停止する。0件は『問題なし』と同義にせず、『必要材料を確認した結果0件』と『材料自体を取得していない』を別状態で扱う。

## 18. Domain Design Engine の出力
専門 Worker 群の結果を統合し、少なくとも以下を生成する。現在の実装で一部生成できているものと、今後追加するものを混同しない。
expected: 成立すべき結果。既存材料の単純反転を無条件に正解としない。
prohibited: 出てはいけない結果・既知失敗・禁止状態。
prechecks: 実装前に成立を確認すべき条件。
completion: Domain の完了条件。
dependencies / impact: 経路・口・依存・影響範囲。
unknowns: 内部材料で解決できない未知項目。
Work Units: 調査・契約・変更・経路確認・試験・環境確認等の作業母数。
evidence coverage: 必須材料、取得材料、未取得材料、各出力の根拠。
2026-08-17 時点では completion_from_materials により expected / prohibited / prechecks / completion の4系統を材料から生成する部品が成立した。ただし、これは Domain Manager の設計能力全体の完成ではない。調査、分割、見積り、資源割当、必須材料集合の自動確定などは別段階である。

## 20. 学習・台帳への還流
未知案件で得た調査結果をその場限りにしない。未知 → 案出し → 選別 → 実証 → 勘定科目/台帳へ登録、という循環を持たせる。次回の同型案件では登録済みの required materials、Worker 構成、成功経路、失敗型、検証面を再利用する。
この還流が成立すれば、設計自動化の成熟とは『LLM がより自由に考えること』ではなく、『一度考えたものが機械側へ回収され、次回の自由判断が減ること』として測れる。

## 21. 実装順序（v0.2）
1. 既存 2DER / RRI / 経路表 / failure memory / self_check / 勘定科目を、5種類の専門 Worker 役へ棚卸しする。
2. 各勘定科目について、既知の required materials と既存 Worker 構成を引ける範囲を実測する。
3. 不足分だけを Worker 機能として設計する。新台帳・新しい口を先に作らない。
4. Domain Manager が required materials と Worker 集合を選び、並列起動できる最小経路を1件通す。
5. Worker 出力を expected / prohibited / prechecks / completion / dependencies / unknowns へ統合する。
6. 統合結果から Contract 群と Work Unit を生成する。
7. 実行後の実測資源を Work Unit に対応付け、将来の見積もり係数を育てる。

## 22. v0.2 の禁止事項
Domain Manager 自身に全台帳・全経路・全環境を逐次調査させない。既知案件でも毎回 LLM に必要材料を自由生成させない。内部に答えがあるのに External Research Worker を起動しない。Worker が取得した材料だけを分母として、必要材料全体を見たように報告しない。0件を、取得不能・未取得・該当なしの区別なしに『問題なし』と扱わない。専門 Worker ごとに新台帳・新しい口を乱立させない。並列実行の結果を単純多数決で統合しない。出所・鍵・母数・衝突理由を保持する。Domain Design Engine を新しい巨大 Manager として独立増設しない。

## 23. v0.2 の完了像
案件が入ると、各 Domain Manager が勘定科目から過去の設計知識を引き、必要な専門 Worker を選択して並列実行する。Worker は担当範囲だけを調査し、根拠・母数・未取得を伴って返す。Domain Manager はそれを統合し、成立条件、禁止条件、実装前検査、完了条件、影響、未知、Work Unit、Contract 群へ展開する。内部に答えが無い場合だけ外部調査へ進み、実証された新知識は台帳・勘定科目へ戻る。
この構造により、2DER は『実装を自動化するシステム』だけでなく、『過去の設計経験を再利用し、未知だけを探索し、設計母数と検証母数を作ってから実装へ送るシステム』へ進む。
