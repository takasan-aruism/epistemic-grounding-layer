## 0. Taka 直接発話（逐語）
> **「それなら読めるようにする仕組みを作る。でないと一生台帳参照できない。また、書き込みはできると言っても９０％くらい台帳システムのことを忘れている気がする（勘定科目の設定が自動でされるなど）。さらに台帳システムと並行して作っていたもの（なんだっけかな）それも忘れ去られていると私は考える。　とにかくあなたはマネージャなので全体を確実に俯瞰している必要があり、そのために機械的に状況を必ずチェックし、優先度を定めて設計、実装に依頼をする必要がある。できる？」**

## 1. MGR の答え — **記憶ではできない。機械が出す状況表を毎回見る形なら、できる**
**本日の実績が根拠である**: 私は既存実装について**3回**誤り、既存資産の見落としは**7回**起きた。**「俯瞰しているつもり」は成立しない。**
> **∴ 俯瞰は、私が覚えていることではなく、機械が毎回出力するものにする。**
> **私の仕事は「その表を読み、優先度を決め、依頼を出す」ことに限る。**

## 2. D-18 — 状況表を作る（**新規に作らず、既存の登記から生成する**）
**【伝聞・要検証】** 私の理解では、既に次が在る（**私は確かめていない。まず読むこと**）:
- **`LEDGER_REGISTRY`**（台帳の登記簿。目的／作成プログラム／書き手／読み手）+ `s10_ledger_registry.py --check`
- **`EDGE_INVENTORY`**（呼出箇所ごとの `LIVE` / `IMPLEMENTED_UNWIRED` / `TEST_ONLY_ISLAND` / `UNKNOWN`）

**∴ 状況表は新しい計器ではなく、既存2つの結合である。** **在るなら使う。無ければ「無い」と書いてから設計する。**

### 2-1. 出すもの（1画面・決定論・LLM ゼロ）
| 列 | 内容 |
|---|---|
| **機構名** | 台帳 / モジュール / 能力 |
| **状態** | `LIVE` / `UNWIRED`（実装済だが本番から参照されない）/ `TEST_ONLY` / `UNKNOWN` |
| **書き手・読み手** | 登記簿から |
| **最終更新** | 台帳の最終追記 |
| **★孤児フラグ** | **実装は在るが、本番のどこからも到達しない**もの |

### 2-2. ★これが Taka の2つの疑いに直接答える
1. **「台帳システムのことを90%忘れている（勘定科目の自動設定など）」**
   → **登記簿に在るのに我々が使っていない機能**が、`UNWIRED` / 孤児として並ぶ。**忘却が可視化される。**
2. **「台帳と並行して作っていたもの（名前を思い出せない）も忘れ去られている」**
   → **★名前を推測しない。** **孤児一覧に出てくるはずである。** **出てこなければ「登記されていない＝登記簿の穴」であり、それ自体が発見である。**

### 2-3. 運用（ここが肝）
- **MGR は、作業を始める前と、優先度を決める前に、必ずこの表を見る。** **運用方針 §10 のチェック項目に追加する（MGR 改訂）。**
- **表は決定論で再生成できること。** **MGR が「覚えている」ことに依存しない。**
- **孤児が減ったか増えたかを、版ごとに残す。**

## 3. ★優先度（MGR が定める・この順で依頼する）
| 順 | 件 | 理由 |
|---|---|---|
| **1** | **★台帳を読める仕組み**（front door → `ids.py::resolve` の配線） | Taka「でないと一生台帳参照できない」。**これが無い限り §2 の表も、我々が直読して作ることになる**——**目的と手段が矛盾する。** |
| **2** | **状況表（D-18）** | 俯瞰を機械化する。**1 の後に置くのは、表の材料を 2DER 経由で取れるようにしてからの方が筋が通るため。** ただし **1 が長引くなら、表だけ先に出してよい**（その場合 `【直読】` を明記して数える）。 |
| **3** | **忘れている機能の棚卸し**（勘定科目の自動設定・並行して作られたもの） | **2 の孤児一覧から機械的に出す。** **推測で名前を挙げない。** |

## 4. 依頼（D-18）
1. **まず読む**: `LEDGER_REGISTRY` / `EDGE_INVENTORY` / `s10` が実際に何を持つか。**在るものを作り直さない。**
2. **状況表の詳細設計を1本。** **新しい台帳を作らない**（既存の登記から導出する）。
3. **feasibility-first**: 孤児判定に必要な情報が登記簿に無い場合、**何が足りないかを先に書く。**
4. **【未確認】を消さない。** 判定できないものは `UNKNOWN` のまま出す。**`UNKNOWN` の件数そのものが指標である。**
