★一文定義（§13）
  Route Worker = 2DERで実際に何がどこからどこへ通ったかを、証拠付きで観測・更新する機構。
  Manager      = 2DERが実際に行ったことと、本来行うべきことを比較し、次に何をすべきかを決める機構。
  境界         = 経路表は事実を言う。Manager はその事実の意味を判断する。

★最重要原則（§0）
  経路表は「実際にどう通ったか」を扱う。Manager は「それで正しいか」を扱う。
  Route Worker にシステム全体の正しさを判断させない。

★Route Worker が確認するもの（§2.1）= A 経路の存在 ／ B 両側証拠（handed_to・received_from）／
  C 実通過 ／ D 観測可能性 ／ E 再確認可能性
★Route Worker が判断してはいけないもの（§3）= 期待された機能か ／ 結果が正しいか ／
  この機能は必要か ／ 他機能との連動が正しいか ／ 全体目的との整合性
★出力は事実状態に限定（§4）= OBSERVED_BOTH_SIDES / OBSERVED_SENDER_ONLY / OBSERVED_RECEIVER_ONLY /
  PASSABLE / NOT_PASSABLE / NO_RECORD / UNKNOWN ／ ★PASSABLE ≠ CORRECT
★Expected と Observed を混ぜない（§6）
★Push と Pull の両方を使う（§7）―― どちらも責務境界を越えない
★完成条件（§11）= ①実行から経路証拠が自動で残る ②両側証拠から区間を自動生成 ③未登録区間を自動検出
  ④既存権限規則で許された区間を自動登録 ⑤人間が登録操作をしなくてよい
  ⑥Pull で経路表と実記録の差分を自動検出 ⑦Worker は「正しい機能か」まで判断しない

  ★経路表を作った後に人間が更新を忘れる構造は完成とみなさない

## ★★★追補（Taka 2026-08-14 19:2x）―― 完成条件を **2段に分ける**

**★MGR の「6.5/8」は 2つの層を混ぜていた。⑧は Route System の完成条件ではなく Manager との接続条件。**

### ★Route System 完成条件（★これだけで 単体完成としてよい）
```
① 経路証拠が自動で残る
② 両側証拠から区間生成
③ 未登録区間検出
④ 許可された区間を自動登録
⑤ 人間の登録操作 0
⑥ Pull による実態差分検査
⑦ 正しさを判断しない
＋ Manager から機械的に取得可能
```

### ★Manager 統合条件（★別に置く）
```
Expected を機械取得 ＋ Route Worker から Observed を取得
＋ Expected ≠ Observed を検出 ＋ 差分から次の仕事候補を生成
```

**★分ける理由（Taka 逐語）**
> これを分けないと、また経路表を完成させようとして Manager を作り始める危険があります。
> まさに今回避けた責任境界違反が、完成条件側から再侵入してくる。

### ★⑥ の中身 ―― 「4機能を作る」ではなく **4つの事実問診**
```
・片側だけの区間は 何本か
・過去に観測されたが 現在観測されない区間は 何本か
・対になるイベント数が 非対称な箇所は どこか
・他区間と比較して 通過数が 異常に少ない区間は どこか
```
**★最後の1つだけ注意（Taka 逐語）**
> 「極端」の閾値を Worker が意味判断し始めると Manager 側へ入りかねない。
> Route Worker なら、パーセンタイルや比率など**事実量を返すところまで**にして、
> 「異常」と裁定するのは上へ渡した方が境界がきれい。

### ★順序（Taka 逐語）
> ⑥が閉じたら、そこで一度 **Route System CLOSED** としてしまっていい。
> その後に Expected の機械化を **Manager Phase** として始める。
> 経路表を経路表として閉じる → 次に Manager、という明確な境界を作れる。

### ★今日いちばん大きい進展（Taka 逐語）
> 単に部品が増えたことより、ようやく 2DER 内部に
> **実行系 / Route Worker / Manager という別々の主体の境界が実装として現れ始めた**ことの方が大きい。
