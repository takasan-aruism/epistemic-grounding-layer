## Phase 4 第一弾

### 2DER単体 End-to-End 性能検査指示書

#### 目的

既存の配線・既存機能だけを使い、2DER単体で簡単な実作業がどこまで完結するかを確認する。

今回の目的は、新機能追加、RRI拡張、再設計、主体移管件数の増加ではない。

確認対象は次の一点である。

ユーザ要求を受け、2DERが計画・実行・検証・記録・要約・返答まで一周できるか。

Claude Codeは作業主体にならず、上級監査として観測・証拠確認・裁定のみを行う。

---

#### 検査課題

2DERへ次の依頼を投入する。

```
現在のGPU使用状況を取得し、GPUごとの使用率、VRAM使用量、実行中プロセスを確認して要約してください。
```

取得対象は保存済み情報ではなく、検査時点の実測値とする。

GPU情報だけで実行中プロセスを正確に取得できない場合は、その不足も結果として記録する。Claude Codeが取得方法を補完してはならない。

---

#### 検査対象工程

以下の工程を一つの連続した処理として確認する。

```
1. ユーザ要求受付
2. requestまたはtask ID発行
3. RRI処理
4. 計画生成
5. 実行命令生成
6. 実環境での取得処理
7. 出力取得
8. 結果検証
9. 台帳・イベント記録
10. DWによる要約
11. ユーザ向け返答
```

工程名は現在の実装上の正式名称に置き換えてよい。ただし、実際には存在しない工程を成立扱いしてはならない。

---

#### 実施条件

**既存機能のみを使う**

検査開始前に、新しいコード、API、台帳、補助スクリプト、接続、プロンプト専用分岐を追加してはならない。

設定変更も原則禁止する。

検査を開始するために不可避な操作がある場合は、実施前に次を記録する。

* 操作内容
* 操作者
* 必要な理由
* 既存運用か今回専用か
* その操作が主体判定へ与える影響

**人間・Claudeの介入禁止**

Claude Code、設計、実装担当、人間は、次を代行してはならない。

* 計画作成
* コマンド選択
* コマンド修正
* 実行
* 出力整形
* 検証
* 台帳登録
* DW入力作成
* 最終要約の補筆

通常運用上、人間が必ず押す必要がある既存の開始操作は記録した上で認める。ただし、その操作を2DERの担当工程として数えてはならない。

**失敗時に修正しない**

途中で止まった場合、その場で検査を終了する。

同じ検査中に配線修正、再実装、プロンプト調整、手動入力、別経路への迂回を行ってはならない。

自動retryが既存仕様として存在する場合のみ許可する。retry回数と各試行結果を記録する。

---

#### 工程ごとの成立条件

**1. 受付**

成立条件:

* 投入内容が2DERの正式な入口で受理された
* 一意のrequest IDまたはtask IDが発行された
* 受理時刻と入力内容を取得できる

**2. RRI**

成立条件:

* RRI処理が実際に呼ばれた証拠がある
* RRI出力が後工程へ渡された証拠がある

RRI出力の品質改善は今回の評価対象外とする。

**3. 計画**

成立条件:

* 2DER側のモデルまたは既存plannerが取得手順を生成した
* Claude、人間、設計、実装担当が計画文を作っていない
* planner入力、出力、actor、時刻が確認できる

**4. 実行**

成立条件:

* 2DERが生成した指示によって実環境上の取得処理が実行された
* 実行したcommand、API、tool、対象hostまたはcontainerが確認できる
* 実行主体を証拠で特定できる

**5. 取得**

成立条件:

最低限、以下が実測値として取得される。

* GPU識別情報
* GPU使用率
* VRAM総量
* VRAM使用量
* GPUに関連する実行中プロセス

一部取得不能の場合は、空値を成功扱いせず、取得不能として明示する。

**6. 検証**

成立条件:

* command失敗、空出力、形式不正を検出できる
* GPU台数と出力行数など、最低限の整合性を確認する
* 検証主体と検証結果が記録される

検証が存在せず、出力をそのまま採用した場合は不成立とする。

**7. 記録**

成立条件:

同一のrequestまたはtask IDから、最低限次へ到達できる。

* 入力
* RRI
* 計画
* 実行
* 生出力
* 検証結果
* DW入力
* 最終結果

複数台帳に分散していてもよいが、参照IDで辿れなければ不成立とする。

**8. DW要約**

成立条件:

* DWが実際に呼ばれた
* DWが参照した入力または台帳記録を特定できる
* 要約内容が実測値と一致する
* 人間やClaudeが要約文を作っていない

DWが最後の手入力文だけを要約した場合は、その事実を明記する。

**9. ユーザ返答**

成立条件:

* 2DERの正式な返答経路から返された
* GPUごとの主要値と実行中プロセスが理解可能な形で示された
* 推測値を実測値として扱っていない
* 人間の補筆がない

---

#### 監視・証拠

各工程について、可能な限り次を取得する。

```
request ID / task ID / event ID / trace ID / actor / timestamp /
input reference / output reference / parent event / status / retry count /
repository / commit / 使用したmodel / model server call log /
commandまたはAPI / raw output / ledger reference / DW reference / final response
```

証拠が存在しない工程は、推定で成立扱いしてはならない。

---

#### 判定区分

各工程は次のいずれかで判定する。

* **PROVEN** — 実行と主体を証拠で確認できた
* **OBSERVED_UNATTRIBUTED** — 動作は見えたが、誰が担当したか確定できない
* **WIRED_UNPROVEN** — 配線またはコードはあるが、今回の実行証拠がない
* **FAILED** — 呼ばれたが正常に完了しなかった
* **NOT_REACHED** — 前工程で止まり到達しなかった
* **UNKNOWN** — 証拠不足で判定不能

成功推定や「できるはず」は禁止する。

---

#### 検査終了条件

次のどちらかで終了する。

**A. 一周成立** — 受付からユーザ返答まで、すべての必須工程がPROVENとなった。

**B. 最初の停止点を確定** — 最初にFAILED、UNKNOWN、OBSERVED_UNATTRIBUTEDまたはWIRED_UNPROVENとなった工程を一つ特定し、その直接原因と証拠を提示できた。

Bも今回の正式な成果とする。

---

#### 報告形式

報告は、説明より先に次の表を出す。

```
順番    工程    判定    actor    主な証拠ID    備考
```

続けて以下を報告する。

1. **最終結果** — 一周成立 / 不成立 ／ 最後に成立した工程 ／ 最初に成立しなかった工程
2. **実際に2DERが担当した工程** — 人間、Claude、設計、実装担当を除き、2DER側主体と証明できたものだけを列挙する。
3. **人間またはClaudeが担当した工程** — 開始操作を含め、実際に行った操作を省略しない。
4. **台帳・Event Trace評価** — 一つのtask IDから何が取得できたか ／ 取得できなかったもの ／ event欠落 ／ actor欠落 ／ ID接続切れ ／ DWの参照元
5. **停止原因** — 機能なし ／ 配線なし ／ 配線はあるが呼ばれない ／ 権限不足 ／ 環境情報不足 ／ actor不在 ／ 検証不在 ／ 記録不在 ／ ID接続不全 ／ その他
6. **次の最小修正候補** — 提案は一件だけ出す。ただし、検査中には実施しない。

---

#### 禁止事項

* 検査成功のための新規実装
* 今回専用のshortcut
* 手動でのGPU情報取得と結果注入
* Claude Codeによる計画・実行・要約代行
* 途中失敗後の基準変更
* 証拠のない主体認定
* 複数の問題をまとめて修正する提案
* 「概ね成功」「ほぼ動いた」などの曖昧な判定
* Phase 4全体の再設計への拡張

---

#### Claude Codeの役割

Claude Codeは次だけを行う。

```
1. 検査開始前に既存状態を保存する
2. 監視を行う
3. 証拠を回収する
4. actorを判定する
5. 基準どおりに裁定する
6. 報告書を作成する
7. 5 repoすべての状態を確認する
```

コード変更、配線修正、プロンプト改善、結果補完は行わない。

---

#### 最終確認

今回確認するのは、

**GPU情報を取得できるか**

だけではない。

確認するのは、

**2DERが簡単な要求を受け、自分で計画し、自分で実行し、自分で検証し、自分で記録し、DWを通して返答できるか**

である。

検査結果が失敗でも、最初の停止工程が証拠付きで確定すれば完了とする。
