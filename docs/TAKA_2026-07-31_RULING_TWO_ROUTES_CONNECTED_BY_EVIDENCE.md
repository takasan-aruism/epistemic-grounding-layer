## 【TAKA裁定】図を実装に合わせる。ただし二経路を証拠で接続する

裁定は選択肢2。

観測をTaskの下流へ移さない。現在の実装に合わせ、8点の一本道を廃止して、以下の二経路として正典を修正する。

```
観測経路：
Request → RRI → Runtime Inspection → Observation → Ledger → DW → Response

改修経路：
Request/RRI → Task → PLAN → GENERATE → VERIFY → APPLYまたはROLLBACK
```

ただし、二経路を独立したままにはしない。

観測経路のObservationおよびLedger上の証拠を、改修経路のTask／PLANが参照する構造とする。

今回のPLANが、直前に取得済みのポート観測を引用せず、同じ観測能力を新規実装しようとしたことを不具合として扱う。

## 次の作業

順番を変更しない。

### 1. Ledgerの既存参照を通す

生出力 blob://... に既存の口から到達できるようにする。

* 新しい台帳を作らない
* 新しいAPIや読み出し口を作らない
* 既存記録が保持する参照を通すだけ
* 一度に直す箇所は1件
* GPU固有実装を入れない

### 2. 修正後に同一依頼でE2Eを確認する

観測経路について以下を確認する。

```
Request
→ RRI
→ Runtime Inspection
→ Observation
→ Ledgerから生出力取得
→ DW要約
→ Response
```

各段階について、IDと実データを用いてPASS／FAILを判定する。

### 3. PLANへの証拠接続は別件として登録する

Ledger修正と同時に実装しない。

次件として、Task／PLANが直前のObservationを参照できるようにする。受入条件は次のとおり。

* PLANの cites_source_ids が空でない
* 対象ObservationまたはLedger記録のIDを引用する
* 既に観測済みの能力を、新規作成対象として重複計画しない
* 証拠から不足が判定された場合だけ改修Taskを作る

## 禁止

* 観測をTaskの下流へ移す設計変更
* GENERATEを押すこと
* 新しい配線総点検
* Execution Architecture全体の再調査
* 新しい台帳・API・ID族の追加
* Ledger修正とPLAN証拠接続の同時実装
* 別の問題を発見したことを理由に今回の1件を停止すること

停止できるのは、データ破壊、既存互換性破壊、ロールバック不能の具体的証拠がある場合のみ。それ以外は欠陥として記録し、指定された1件を完了する。
