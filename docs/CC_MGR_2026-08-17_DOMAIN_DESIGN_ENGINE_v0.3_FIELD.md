## 2. ★§13 の前提を数で締める ―― 勘定科目は **5件**

```
実体 = rri/rri/rthread_chart.json（chart_version ＋ accounts ★5）
```
v0.2 §13 は「案件を科目で分類 → 過去の required materials を引く」を第一原則にしている。
**★引く先が 5件しかない** ∴ 当面は**大半が未知処理へ落ちる**。

**★V3 の書き方**:
- 「既知は参照へ落とす」は**目標**であり、**現在の既定経路ではない**。
- 成熟度は **`accounts` の件数**と **`required materials` を引けた案件の割合**で測る（★どちらも今日から数えられる）。
- **★「科目から引ける」を前提に設計を組まない**（組むと 5件の上に全体が乗る）。

## 3. ★§7 環境 ―― 「見ている物」と「見ていない物」を割る

```
★見ている（probe_environment）= workspace ／ runner identity ／ timeout・spawn 失敗 ／ 必要成果物
★見ていない = OS ／ ドライバ ／ GPU・CPU・RAM ／ 権限 ／ 常駐サービス ／ 依存パッケージ
```
**★∴「環境を確認している」と一括で書かない。** 現在は**実行環境の破損検知**であり、**基盤の棚卸しではない**。
v0.2 §7 の「コードだけ試験して環境未確認」は**半分当たっている**（実行環境は見ている／基盤は見ていない）。

## 5. ★§17 材料完全性 ―― 実装で確認済み、**ただし穴は呼び手側**

```
在る = `completion_from_materials` は required に無い材料で `missing_material` 停止（★部品に既に在る）
★穴 = required を書くのは ★呼び手。2026-08-17 に MGR が 4つしか書かず relay_chain が落ちた
      → materials_used は「渡された材料」しか映さない ∴ 落とした事が表に出ない
      → しかも値が全部 0 だったので 件数も動かず 完全に隠れた
```
**★V3 に明記**: 「0件の扱い」だけでは足りない。**`required` を誰が確定するか**を決めない限り、
**分母を出す仕組みごと空振りする**。当面の実装は「渡した材料 = required」を機械が強制する形が最小。

## 6. ★§14 External Research ―― 禁止の前に不在

v0.2 §22 は「内部に答えがあるのに外部検索を起動しない」と禁じている。
**★現状は口そのものが 0件** ∴ **禁止条項は現時点で発火しない**。
**V3 の書き方**: 「外部調査は**未実装**。禁止条項は**実装時に効く**」と分けて書く（★不在を規律で語らない）。
