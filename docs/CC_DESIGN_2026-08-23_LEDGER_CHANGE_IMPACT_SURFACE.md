## 0. 結論を先に

**台帳変更で壊れるのは「欄の名前に直接触っている読み手」だけである。**
アクセサ（公開関数）を通す読み手は、台帳が変わっても壊れない。

実測:

```
台帳に触るファイル              23
  欄名への直接アクセス（総数）   93 箇所
  アクセサ呼び（総数）           76 箇所
★アクセサを1度も使わず直触だけ  10 ファイル   ← ★これが 台帳変更の 事故面
```

**アクセサは既に十分ある**（`request_thread` 24関数 / `workcell` 30関数 / `etrace` 12関数）。
足りないのは器ではなく、**使われていないこと**である。

## 3. どの欄が何箇所から触られているか（★改訂の重みはこれで測る）

```
findings              5      ← ★事故②の欄
review                4
goal                  4
contract              4
finding_dispositions  3
run_id / knowledge_packet / implementation_packet / finish_reasons  各2
supersedes            1      ← ★本日 私が足した欄
```

**`findings` / `review` / `contract` を変えると、それぞれ 3〜5 箇所を同時に直す必要がある。**
逆に言えば、**この3つにアクセサを付ければ改訂コストが一番下がる。**

## 4. 「柔軟にしておく」ための1点（★増やさない）

**新しい層を作らない。既にあるアクセサを「唯一の読み口」に寄せるだけでよい。**

理由:
- `workcell` に 30、`request_thread` に 24、`etrace` に 12 の公開関数が**既に在る**
- `request_thread` は **module 外からの `_read` 呼び出しが 0 件**（MGR 実測）＝ **既に理想形**
- 一方 `workcell` は `_read_events` が **module 外から 36 箇所**呼ばれている ＝ ここが緩い

∴ **`rri` が既に達成している形を `dw` にも当てる**のが最短で、新しい設計を要しない。

**★ただし一斉に寄せてはいけない。** 本日の実測で、直触は 93 箇所ある。
一度に触ると「前と同じ数字」で検証できなくなる（今日の私の修理はすべて before/after を同じ入力で測った）。

## 5. 改訂の順序（意見。決めるのは MGR と Taka）

1. **`findings` にアクセサを付ける**（5箇所・事故②の欄・明細と繋ぐ時に必ず変わる）
2. **`review` / `contract`**（4箇所ずつ）
3. 残りは**台帳が実際に変わる時に、その欄だけ**

★「全部一斉に直す」は勧めない。★理由は上記の検証可能性。

## 6. 明細（rthread）側について

**明細は既に良い形である。** module 外からの `_read` / `_append` が **どちらも 0 件**（MGR 実測）。
∴ **明細の欄をいくら増やしても、読み手は公開関数の返りが変わるだけで壊れない。**

**★危ないのは明細ではなく DW 側**である。明細を DW と繋ぐ時、
DW 側の 10 ファイル（直触だけ）が受け皿になると、**そこで欄名の不一致が起きる。**
