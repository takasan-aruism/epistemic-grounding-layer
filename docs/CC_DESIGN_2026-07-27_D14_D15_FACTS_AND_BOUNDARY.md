## 1. ★D-14 の4問のうち3問は、帳簿を読まずに答えられた（判断の理由を書く・v1.3 §2-1）

### 1-1. 勘定科目はどう決まるか【監査:CC-α・コード構造】
**Taka の指摘は正しい。エンベーディングである。MGR の「凍結 chart から選ぶ」は誤りだった。**

**2本の別々の系統が在る。MGR（と私）はこれを1つと誤解していた:**

| 系統 | 実体 | 素性 | 結果 |
|---|---|---|---|
| **(A) 決定論マイニング** | `s_mine_accounts.py`（2b-1） | cooc / band / kind（**埋め込みを使わない**） | **`chart_status = NO_STABLE_STRUCTURE`** — 「安定な構造は record 種別の自明分割しか無い」として**chart を捏造せず、命名へ進まなかった。正当な結論** |
| **★(B) 埋め込み軸** | `s_embed_axes`(2b-r1) → `s_account_axes`(2b-r2) → `s_rthread_2br3`(2b-r3) → `s_account_axis_names` | **埋め込み（cosine / silhouette）** | **軸を発見 → COHERENT のみ凍結 → Taka 承認で版を上げる → LLM 3-seed consensus で命名** |

**∴「勘定科目はエンベーディングを使っており自由に作られる」は (B) のことである。**
**私が最初に見た `NO_STABLE_STRUCTURE` は (A) の結論であり、これを「勘定科目が無い」と読むのは誤読である。** **私はその誤読を報告する寸前まで行った。書く前に (B) を見つけたので出していない。**

**決まり方の要点（`s_account_axes.py` docstring と本体より）:**
- 軸が本物か寄せ場かを **silhouette vs sub-silhouette** で**決定論裁定**する（`COHERENT` / `CATCH_ALL`）。
- 所属は **絶対 cosine 閾値を使わない。** **負の制御（素性 shuffle）に対する相対** で決める。
  > コメント逐語: 「e5 anisotropy で全ベクトルが高 cosine=絶対閾値は退化。**裁定A: 幻覚的絶対定数の禁止**」
- **多重所属が設計上は可能。** 全軸が閾値未満なら **「その他」**。
- 命名は LLM だが、**未成立は `UNRESOLVED_NO_CONSENSUS`（捏造ゼロ）。**

**∴ 系統 (B) は、Taka が繰り返し述べてきた原則（存在するかどうかを決定論で確定し、LLM には選ばせる／作らせない）が、既に実装されている場所である。**

### 1-2. 「未確定・未定」に相当する状態は在るか【監査:CC-α・コード構造】
**在る。名前は「その他」（台帳上は `unclassified: true`）。**
- 定義: **全軸で density が負の制御を上回らない**とき。`s_account_axes.py` の membership 規則。
- **これは MGR が発明した「仮勘定」とは別物である。**
  - **仮勘定**＝後で確定して**振替える**前提の保留。
  - **その他**＝**閾値未満という測定結果そのもの。** **振替を前提としていない。** 次に軸が増えれば自然に変わる。
- **`2b-r3` の `_meta` 逐語**: 「空/全非QUALIFIED=NO_CANDIDATE（**その他優勢継続=正当**）」
  **∴「その他が多いこと」は既に正常状態として明文化されている。異常でも欠損でもない。**

**【設計:CC-α】∴ MGR が §4-1 で撤回したのは正しい。** **新しい機構は要らない。「その他」が既にその役を果たしている。**
**ただし「多義の明細をどう記帳するか」を「その他」で代用してよいかは別問題である。** **「その他」は軸との距離の話であり、「読み方が複数ある」の話ではない。** **同じ入れ物に入れると、2つの異なる未確定が混ざって数えられなくなる。** **後段の設計で分ける。**

### 1-4. 「凍結」の実際の意味【監査:CC-α・コード構造】
| 何が | 状態 |
|---|---|
| **凍結されるもの** | **軸の集合（versioned Frozenset）と、その方向ベクトル。** 版として固定される |
| **凍結されないもの** | **要素の所属。** density で都度計算される。**新しい記録は自動的に判定される** |
| **自由なもの** | **新しい軸の発見。** 埋め込みクラスタリングが `QUALIFIED` を出す |
| **機械が勝手にやらないこと** | **★凍結（版上げ）。** `2b-r3` は `propose only`。**`FREEZE_APPROVALS` に Taka の承認が記録された時だけ版が上がる** |

**∴「触らない」の正しい意味は「既に承認された版を書き換えない」であって、「もう増えない」ではない。**
**MGR が制約として繰り返した「無い科目を作らない」は誤りである。** **科目は増える。増やし方に承認が要るだけである。**

## 4. ★境界を構造として成立させる手段（v1.4 §4・実装可否と Taka 判断を分ける）

**現状の事実**【監査:CC-α】:
```
再現: id -un        → takasan  （groups に sudo, docker を含む）
再現: stat -c '%U:%G %a' egl/DESIGN_EVIDENCE_LEDGER.jsonl rri/rri_records.jsonl

```
**∴ Claude のシェルと 2DER のプログラムは同一 OS ユーザで動いている。** **∴ ファイル権限では両者を区別できない。** **今の配置では、境界は権限として実装不可能である。**

### 4-1. 候補（実装可否で分ける）
| 案 | 内容 | 我々だけで可能か | 効果 |
|---|---|---|---|
| **A. 数える（現行）** | 直読に `【直読】` を付けて数える | **可能。既に実施中** | **規律。構造ではない。** 数字が減らなければ効いていない |

| **C. OS ユーザ分離** | 2DER を別ユーザで動かし、台帳をそのユーザ所有・`0600` に。Claude は front door 越しにしか触れない | **不可能。Taka の判断と作業が要る**（ユーザ作成・所有権変更・sudo） | **構造として本物。** ただし §4-2 の副作用 |

### 4-2. ★C には既知の副作用が在る（先に出す）
```
再現: ls egl/structure/s*.py | wc -l                     → 46
再読: そのうち台帳を直接 open/json.load しているもの      → 39
```
**∴ 台帳を `0600` で他ユーザ所有にすると、`egl/structure/` の研究スクリプト39本が全て動かなくなる。**
**∴ C を採るなら「プログラムは中の職員だから読んでよい」を、ユーザではなく別の単位で表現する必要がある**（例: 2DER 側ユーザで実行する／sudo 越しに走らせる）。**設計が必要であり、今日の話ではない。**

### 4-3. 【設計:CC-α】私の推奨
**B を先に、C は Taka 判断待ちで保留。** **A は続ける（数字が判断材料になる）。**
**理由**: **境界が破られる原因は意志ではなく経路の欠落である**（§2-3 で実証済）。**経路を作らずに権限だけ閉じると、我々は仕事ができなくなり、必ず抜け道を作る。** **これは規律の失敗ではなく設計の失敗になる。**
**∴ 順序は「読める経路を作る → 直読の数が実際に減るのを見る → 減ってから権限で閉じる」。**

### 4-4. Taka の判断が要るもの（MGR 経由）
1. **C（OS ユーザ分離）に進むか。** 進むなら **Taka の環境作業（ユーザ作成・所有権変更）が必要**であり、**研究スクリプト39本の扱いを先に設計する必要がある。**
