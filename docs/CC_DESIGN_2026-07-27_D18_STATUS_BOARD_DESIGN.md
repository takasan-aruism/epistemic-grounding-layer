## 2. ★計器自身の健忘（3件・これを直さずに結合しない）【監査:CC-α】

### 2-1. 材料の鮮度が揃っていない
```
再現: stat -c '%y %n' LEDGER_REGISTRY.jsonl EDGE_INVENTORY.jsonl REACHABILITY.jsonl FILE_MANIFEST.jsonl
2026-07-22 08:00  LEDGER_REGISTRY.jsonl     ← ★5日古い
2026-07-26 05:02  EDGE_INVENTORY.jsonl
2026-07-26 05:01  REACHABILITY.jsonl
2026-07-26 05:02  FILE_MANIFEST.jsonl
```
**∴ 台帳側の登記は 07-22 の姿、到達性側は 07-26 の姿である。** **結合すると、日付の違う2枚を1枚に見せることになる。**
**★本日作った `twoder/ledger_query.py`（削除予定）も、今日の作業も、登記簿には載っていない。**

### 2-2. ★`TODAY` がハードコードされている — 計器が日付を覚えていない
```
s10_ledger_registry.py:26   TODAY = "2026-07-22"
```
**∴「放置日数」は常に 2026-07-22 基準で計算される。** **今日実行しても、5日分の放置が消える。**
**★これは、俯瞰を機械化するための計器が、まさに健忘している例である。** **Taka の指摘そのものが計器に起きている。**

### 2-3. ★`s4_edges.py` に `--check` が無い

再現: grep -q '\-\-check' s4_edges.py   → 無し

**∴ 状況表の生成器は、材料を再生成してはならない。読むだけにする。**

## 3. ★粒度の問題（feasibility-first・MGR §4-3）— **Taka の問いに直接効く**

**表に出せる「機構名」は2粒度しかない:**
| 粒度 | 出せるか | 例 |
|---|---|---|
| **台帳** | 出せる（`LEDGER_REGISTRY`） | `ACCOUNT_MEMBERSHIP_v2.jsonl` |
| **ファイル/呼出** | 出せる（`EDGE_INVENTORY`） | `s_account_axes.py:123` |
| **★能力** | **★出せない。そういう単位が登記されていない** | 「**勘定科目の自動設定**」＝ `s_embed_axes` → `s_account_axes` → `s_rthread_2br3` → `s_account_axis_names` の4本＋台帳6つ |

**∴ Taka が名前を思い出せない「並行して作っていたもの」が能力なら、孤児一覧に1行としては出てこない。** **4本のファイルと6つの台帳に散る。**
**∴ MGR §2-2 の期待「孤児一覧に出てくるはず」は、そのままでは成立しない可能性がある。**

### 3-1. 私の提案（推測で名前を挙げない・MGR の規律を守ったまま）
**能力を新しく定義しない。** **代わりに、孤児を「まとまり」で見せる:**
- **孤児を、`writer` の**ディレクトリ**と**genesis コミット**でグループ化して出す。
- **同じ初出コミットから生まれた孤児は、同じ作業の産物である可能性が高い。** **∴ グループが「並行して作っていたもの」の候補になる。**
- **★名前は付けない。** **`genesis` の件名を raw のまま並べる**（`s10` が既にその方針で件名を保持している）。**人間が見て思い出す材料にする。**

**∴ これは推測ではない。** **「同じコミットで生まれた」という決定論の事実だけを使う。**

## 5. 優先度について（MGR §3 への同意と1点の補足）
**MGR の順序（1 台帳を読める仕組み → 2 状況表 → 3 棚卸し）に同意する。**
**補足**: **状況表を先に出す場合、それは `【直読】` である。** **ただし「プログラムが読む」形なので、Taka の選択肢2（事前に用意したプログラムが読む）の形は満たしている。** **足りないのは front door から呼べることだけである。**
**∴ 数えるべきは「我々が grep した回数」であって、「生成器が台帳を読んだ回数」ではない。** **区別する。**
