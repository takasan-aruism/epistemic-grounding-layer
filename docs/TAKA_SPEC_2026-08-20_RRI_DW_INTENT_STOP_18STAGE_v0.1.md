## 0. 結論（★逐語）

```
2DERは「依頼を受けたら最後まで流す」システムではなく、ユーザ意図に応じて1〜18の必要区間だけを使う。
RRIは単なる6分類器ではなく、未確定な意図を会話的に精緻化し、今回の目的・納品形式・停止地点を確定する入口である。
RRI→DWの連動点で、GOAL / WORK_KIND / DELIVERABLE / STOP_AT / EVIDENCE / AUTHORITY / DO_NOT を
  機械可読な契約として固定する。
INVESTIGATE / OBSERVE / DECIDE / DESIGN / VERIFY / REPORT は、IMPLEMENTとは別の仕事として完了可能でなければならない。
既存18段は、特定正常系のみを繋いだ結果として隠れた前提・到達不能・head-of-line blocking・納品形式固定などを
  抱えている可能性が高い。18段すべてを固定メニューで再調査する。
調査は自由記述で行わせない。対象・問い・判定語・根拠形式・停止条件を固定した『調査メニュー』として2DERに与える。
Claudeは通常設計者ではない。原則としてFrontから依頼投入、観測、正規記録確認、authority / safety上申のみとする。
```

## 3. 設計原則（★逐語）

```
A 意図が確定している依頼は、その意図に従う。不要な追加工程を起動しない。
B 意図が未確定なら、RRIは必要情報を精緻化する質問をユーザへ返す。曖昧さを下流へ押し込まない。
C 1〜18は必ずしも全区間を走らない。目的を満たした地点で終了できる。
D RRIとDWは『前後に並んでいる』だけでなく、どの情報を受け渡した時に連動成立とするかを契約で定義する。
E 各段の存在だけでなく、入力・出力・対象範囲・事前条件・次段・実接続・停止可能性を機械可読にする。
F 調査は自由回答にしない。固定メニューを与え、在る/部分的/無い、またはGO/STOP等の有限語彙で答えさせる。
G 実装能力より『適切な段で止まる能力』を優先する。
```

## 5. RRI→DW 連動契約の 7要素（★§0 より）

```
GOAL / WORK_KIND / DELIVERABLE / STOP_AT / EVIDENCE / AUTHORITY / DO_NOT
```

## 12/15. 判定の 有限語彙（★§15 逐語）

```
EXISTS / PARTIAL / ABSENT / CONFLICT / UNVERIFIED
★各判定には 必ず evidence_refs と observed_value を付ける。
★推測で 欄を 埋めない。
★不足が あっても 修正案へ 進まず needs_design=true として 停止する。
★納品物は 調査表のみ。Python関数・sandbox artifact を 納品物に しない。
```

## 14. 調査の順序（★逐語）

```
Phase A 1〜8   意図確定・入口・routing。最優先。ここが誤ると後段すべてが無駄になる。
Phase B 9〜12  契約・task化・run gate・dispatch。仕事種別と実行適格性を確認する。
Phase C 13〜18 PLAN/生成/試験/監査/完了。IMPLEMENT正常系の焼き付きと非実装成果の扱いを確認する。
Phase D 横断   declared_next と observed_connection、stop_at、authority、永続性、recovery path を照合する。
```

## 18. Claude の 位置づけ（★逐語・★私の 行動規範）

```
通常運転では設計者・実装者・裁定者として使わない。
Frontから依頼を投入する、正規記録を観測する、authority/safety/不可逆変更を上申する、という外部MGR補助に限定する。
Claudeが途中処理を代行した場合、その変更・判断・bootstrapは必ず2DERの正規記録へ還流する。
Claudeが『止まったから代わりに調査/設計/実装する』ことを通常運転の開始条件にしない。
```

## 20. 完了条件（★逐語）

```
RRIが意図未確定時にユーザへ精緻化メッセージを返せる。
意図確定後、WORK_KIND / DELIVERABLE / STOP_AT が機械可読な契約として下流へ渡る。
非IMPLEMENT仕事がコード生成なしで正常完了できる。
各StageのM1〜M16調査表が正規記録から取得できる。
特定正常系だけに依存した隠れ前提が、CONFLICT/PARTIALとして事前に検出される。
1〜18のどこで正常終了可能かがwork_kindごとに定義される。
Managerの運行管理とRRIの意図確定が混同されない。
Claudeなしで、調査→設計→必要な場合のみ実装、という順序を2DER自身が守れる。
```

## 21. 実装順（★逐語）

```
P0 RRI→DW連動契約に WORK_KIND / DELIVERABLE / STOP_AT を持たせる設計を2DER自身に行わせる。
P1 INVESTIGATEを最初の非IMPLEMENT完了経路として成立させる。
P2 1〜8をM1〜M16で調査し、意図確定・routingの欠陥を先に洗い出す。
P3 9〜12を調査し、task化/run gate/dispatch/Manager HOLを整理する。
P4 13〜18を調査し、IMPLEMENT正常系の焼き付き・証拠・監査・完了を整理する。
P5 OBSERVE / DECIDE / DESIGN / VERIFY / REPORT を順に非IMPLEMENT完了可能にする。
P6 Current Workの1テキスト表示を正規状態から生成する。
```
