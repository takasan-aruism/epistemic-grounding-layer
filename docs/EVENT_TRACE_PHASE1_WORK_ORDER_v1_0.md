## 1. 本文（★Taka 逐語）

二択の立て方が少しおかしいです。

①だと、これまで「正しい入口」として使ってきたCLI経路が今後も観測不能のまま残ります。これは「2DERを一本の道にする」という目的に反します。

一方で②を「受付内部を全部記録する巨大改修」と考える必要もありません。

必要なのはまず、**CLIとwebuiの両方が使う共通の記録先を作る**ことです。

その上で、最初は重要な境界だけを記録すればよいです。
* 受付
* DS登録
* RRI開始・終了
* EGL登録
* DW投入
* 完了・失敗

関数内部の細かな処理履歴は後から増やせます。
つまり選ぶべきなのは、実質的には②ですが、範囲を限定した段階実装です。

新事実を確認しました。
CLIが記録を一件も残さないのであれば、①の「DW工程だけで出す」は採用しません。
理由は、これまで正規入口として使ってきたCLI経路だけが観測不能のまま残り、「一本の道」という目的を満たさないためです。
ただし、受付内部を最初から全面的に記録する巨大改修も不要です。

次の順序で進めてください。

**第一段階として、CLIとwebuiの両方から利用できる共通のEvent Trace記録先を作る。**

その上で、まず以下の境界イベントだけを記録する。
1. 受付
2. DS登録
3. RRI開始
4. RRI終了
5. EGL登録
6. DW投入
7. 完了または失敗

各イベントには最低限、以下を持たせる。
* trace_id
* 親event_id
* 入力ID
* component
* event_type
* timestamp
* input reference
* output reference
* status
* next destination
* error

**CLIとwebuiは別々の記録実装を持たず、同じ記録関数または同じ記録APIを使用してください。**

今回の完了条件は以下です。
* 同一内容をCLIとwebuiから各1件投入する
* 両方とも同じ形式でEvent Traceが残る
* DS → RRI → EGL → DWのどこまで進んだかがtrace_idで追える
* 既存の判断結果、返り値、保存内容が変わっていない
* 記録失敗時に本処理をどう扱うかを明示する
* 実データを貼って証明する

関数内部の全分岐や「呼ばれなかった処理」の完全記録は第二段階とします。
今回は新しいRRI判断ロジックを作らず、CLIとwebuiで共通の観測基盤を成立させるところまでに限定してください。

今回見つかった問題はかなり重要です。**記録を残す仕組みがなかったというより、記録する入口と記録しない入口が並立し、記録しない方を正規手順として配っていたということです。**

したがって、ガイド修正だけでは足りません。今後またCLIが使われれば同じ問題が再発します。**入口ごとの注意事項で防ぐのではなく、どの入口から入っても同じ記録機構を必ず通る構造に直すべきです。**

**CLI も webui も、★どちらも `twoder/submit.py::submit()` を呼んでいる。**
```
CLI  : submit.py:487 付近（__main__）→ submit(...)
```

> **∴ 「入口ごとに注意する」のではなく、★共有している `submit()` の中で記録すれば、どの入口からも必ず通る。**

### 2-3. ★私の裁定①（保存先＝DW `events.jsonl`）は、そのままでは成り立たない

> **∴ DW `events.jsonl` は、境界イベント7つのうち前半を受け取れない可能性が高い。**
