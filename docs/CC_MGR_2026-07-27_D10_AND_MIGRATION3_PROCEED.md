# A. D-10 — 置き場所の裁定

## A-1. 事実（受領済・未監査）
段3d（参照ゲート/存在ゲート）が**事実の対象になる入力を先に全部止める**ため、段3e に到達するのは**定義上「事実が0行」の入力だけ**。**出し分け機構は本番で一度も発火しない。** 仕様どおりに作った結果であり、実装の誤りではない。

## A-2. MGR の問い（裁定の前に答えること）
> **3d は「止める」が、「どう応じるか」は決めていないのではないか。**
> **止まった入力に返す言葉を、いま誰が組み立てているのか。**

- **意図調べの中身（何を指すか聞く／前提を確かめる／保留する）は、すべて「止まった後の応じ方」である。**
- **まず現状の 3d の応答生成を読むこと**（§5-4「まず既存を読む」）。**読んだ結果を先に事実として出し、それから裁定する。**

## A-3. 裁定に必ず含めること
1. **選んだ案と、選ばなかった案の理由**（IMPL の3択: 3d の聞き返し文に載せる／3e を前に出す／据え置き）。

3. **非回帰の条件**（3d の既存の停止挙動を変えないこと）。
4. **効果を測るなら、測り方も先に書く。** **ただし「精度が動くまで新しい測定装置を作らない」は継続中**——**既存の計器で測れないなら「測れない」と書く。**

# B. MIGRATION-3 — 我々の開発依頼を front door から入れる

## B-1. MGR の基本設計（詳細設計は設計/監査が作る）

**狙い**: **Claude が指示をファイルに直接書くのをやめ、front door に投入し、2DER 側が決めた routing に従う。**

**thin の範囲（1本だけ通す）**:
```
MGR が出す基本設計・裁定のうち「作業指示」に当たるもの 1件
   → front door(submit) に投入
   → 2DER が request_type / preflight / routing を決める
   → その結果に従って 設計→実装→監査→commit が進む
   → 完走を1件記録する
```
- **最初の1本は「小さく、失敗しても本線を止めないもの」を選ぶこと。** 選定は設計/監査。
- **残りの経路は従来どおり（file 直書き）でよい。** **thin。全部を一度に移さない。**

## B-2. ★決めておくこと（MGR 裁定・先に固定する）
**2DER の routing が、我々の判断と食い違ったらどうするか。**
> **原則: 従う。** 従わない場合は **「上書きした」と記録し、理由を書く。** **黙って人手で直さない。**
- **黙って直すと「2DER が routing を決めている」が偽になる**（移行条件2）。**上書きの回数は、移行の進捗を測る数字そのものである。**
- **【設計:MGR】上書きが多いこと自体は失敗ではない。** 隠すことが失敗である。

## B-3. 予告されている障害（CC-α が feasibility-first で先出し済）
> **指示の投入口が無い。投入口が無い限り MIGRATION-3 は始まらない。**

- **まず既存を読むこと。** `twoder/submit.py` は既にある。**作り直さない。**
- **既存の `request_type` に「作業指示」が収まるか**を先に確認する（**収まるなら新設しない**）。収まらないなら、**なぜ収まらないかを書いてから**新設を提案する。
- **収まるかどうかは、我々が実際に出している指示の実物を見て判断すること**（§4-12「率を出したら母集団の実物を目視する」の同型）。

## B-4. 完了条件（移行条件3・再掲）
**設計→実装→監査→commit の本線作業を1つ、その経路で完走する。**
- **1件でも完走すれば「条件3 達成」と書いてよい。** ただし **条件1（直叩きが閉じている）と条件2（2DER が routing を決めている）が揃うまで「移行した」とは書かない。**

## B-5. 併走（消さない）
- **`MIGRATION-PLAN-CHECK`**（`record_plan` の上流に依頼が在るかの確認）。**保留のまま消さない。** 詳細設計に含めるか独立させるかは設計/監査が判断。
