## 5. ★設計提案 — 「A か B か」ではない
> **(B) を段として使い、(A) の様式を借り、パターンは我々の証拠から書き起こす。**

1. **段 = (B) の 3d 段を一般化**。`GATE_ID` 1個固定を**ゲート表**にし、`detect()` を「登録された全ゲートを回して最初に triggered したものを返す」に変える。**配線は既存のまま**（submit.py の呼び方は不変）。
2. **様式 = (A) のスキーマを採用**（`ambiguity_type` / `clarification_slots` / `false_positive_notes` / 抑制カウンタ）。**`clarification_slots` があるので「聞き返し文」を捏造せず構成できる。**
3. **データ = 34 パターンを wholesale で入れない。** 証拠のある1クラス（指示先のない指示語）から**小さく起こす**。
4. **★検出規則は「表層一致」だけにしない（ここが肝）**
   - (A) は表層一致のみ。だから「これ」「前の件」は**指示先が文脈で解決できる時にも発火**する（＝25%の正体）。
   - **我々の失敗は「指示語がある」ことではなく「指示語の**指す先が無い**」こと**である。
   - → 規則は **`指示語の表層 AND 束縛できる先が無い`**。後半は**構造で判定できる**（文脈が空か、セッションに束縛可能な直近対象があるか）。
   - **この「先が無い」判定こそ LLM にできない部分**（3度の目撃どおり、model は空白を埋める側に倒れる）。**そして機械にはできる。**
5. **LLM の使い所を限定**: (A) は Qwen で意味的補完をするが、**実行時の曖昧判定に LLM を使わない**。使うなら**パターン DB を育てるオフライン側**（候補生成）に限る。＝今日ずっと出ている原則「**機械が決められることを全部引いてから LLM に渡す**」。
