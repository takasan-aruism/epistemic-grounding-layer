# 2DER / RRI 台帳・明細システム 設計思想メモ v0.1

**著者: Taka（2026-08-23）／ 記録: Claude Code（逐語・要約せず全文）**

## 1. この資料の位置づけ

本書は、現在の2DERに存在する台帳・明細機能を全面的に仕様化するものではない。

目的は、これまで部分的に実装されてきた明細機能について、本来意図していた設計思想を再提示し、現在の実装との差分を調査するための基準を置くことである。

実装詳細・既存schema・既存API・既存台帳については、2DERの現物を優先して確認すること。

新しい台帳・state・ID体系を、この資料だけを根拠に追加してはならない。

---

## 2. 台帳と明細は2DERの中核である

2DERにおける台帳は、単なるログ保存場所ではない。

また明細も、長い依頼文を読みやすく分割した文章片ではない。

基本思想は、

ある依頼に関して2DERが受け取った情報、調査した情報、判断に使用した情報、生成した情報、失敗した情報、最終的に得た結果を、後から再利用可能な形で蓄積すること

にある。

したがって、

依頼 → 処理 → 回答 → 終了

ではなく、

依頼
→ 明細化
→ 不足情報の発見
→ 追加情報取得
→ 明細の充足
→ 処理
→ 結果・失敗・判断の追記
→ 類似案件へ再利用

という循環を想定する。

---

## 3. 長文分割は最初の一歩にすぎない

ユーザーが長文を投入した場合、そのままでは台帳上の具体的な明細として扱いづらい。

そのため最初に意味単位へ分割する。

ただし、現在確認されているような、

* 箇条書き記号
* 行頭番号
* 単純な文字数
* 単純な句点

だけを最終的な明細単位とは考えない。

目標は、

1明細 = 後から独立して参照・評価・補足・関連付けできる意味単位

である。

分割は明細の「生成」であって、明細の完成ではない。

---

## 4. 明細は後から成長する

最初の明細が例えば、

徳川家康の関ヶ原での働きを整理する

だけだったとしても、RRIによる調査後には、その明細または関連明細へ、

* 調査結果
* 出典
* URL
* 出典中の該当箇所
* 取得日時
* 他資料との一致・不一致
* 関連人物
* 関連する他明細
* 最終回答での使用状況

などが付加され得る。

開発の場合も同様である。

例えば、

このAPIの認証方式を確認する

という明細には後から、

* 対象repo
* file
* function
* API
* framework
* library/version
* 公式documentation
* 実コード
* 関連task
* finding
* artifact
* test evidence
* authority
* 過去の類似障害

などが接続され得る。

したがって明細は、静的な文章片ではなく、

依頼に関する知識を蓄積していく単位

として扱う。

---

## 5. 原文は必ず保持する

明細化・分類・要約によって原文を失ってはならない。

最低限、

原文
原文中の位置
親request
明細順序

へ戻れる必要がある。

要約・解釈・分類結果は原文の代替ではなく、付加情報である。

表示上200文字へ省略することは許容できるが、保存データそのものを切断してはならない。

---

## 6. 種別は有用だが、それ自体が目的ではない

現在検討している、

FACT
CHANGE
SPEC
TEST
CONSTRAINT
GOAL

という種別は有用である。

特に、

* 何が事実なのか
* 何が変更要求なのか
* 何が仕様なのか
* 何が試験なのか
* 何を壊してはいけないのか
* 何をもって終了とするのか

を分離できる。

ただしこれは明細の情報構造の一部にすぎない。

action や goal のように原文を言い換えるだけの欄を機械的に増やすことは目的ではない。

情報量が増える、照合可能になる、再利用可能になる情報を優先する。

---

## 7. 勘定科目

明細に勘定科目を付ける設計は維持する。

勘定科目は固定taxonomyだけを想定しない。

EmbeddingとLLMを利用し、

* 既存科目への自動割当
* 新しい意味群の発見
* 科目候補の生成
* 類似明細からの科目拡張

を可能にする。

現在この仕組みはかなり進んでいるため、新しい明細設計では既存の科目割当機構とどう接続するかを先に調査すること。

---

## 8. RRIの役割

RRIは「依頼を分割するシステム」ではない。

本来の役割は、

依頼を理解可能な単位へ分け、その依頼を処理するために不足している情報を発見し、必要な情報を取得し、設計・回答・実行に必要な材料を揃えること

である。

概念的には、

REQUEST
→ SEGMENT
→ CLASSIFY
→ WHAT_IS_KNOWN
→ WHAT_IS_MISSING
→ RESEARCH
→ EVIDENCE
→ RELATE
→ READY

という流れになる。

実際の既存stateや処理名は現物を優先する。

---

## 9. 情報源・証拠を明細へ接続する

調査によって取得した情報は、回答文にだけ使用して捨てない。

最低限、

* source type
* source identifier
* URL
* document/artifact ID
* source span
* evidence text
* retrieved time
* verification state

等を、既存構造が許す範囲で明細へ関連付ける。

例えばWeb調査なら、

「徳川家康は〜した」

だけでなく、

この主張はSOURCE-Xのこの箇所を根拠にした

まで戻れるようにする。

開発なら、

「この関数はこう動く」

に対して、

repo/file/symbol/commit/test/eventのどれを根拠にしたか

を辿れるようにする。

---

## 10. 2DER内部IDとの関係

明細は他の2DER上の存在を参照できる必要がある。

対象例：

* TASK-
* ITEM-
* ART-
* ETR-
* finding
* approval
* requirement
* route
* 他明細

単なるID文字列だけでなく、可能なら関係の意味も保持する。

例えば、

derived_from
evidence_for
depends_on
supports
contradicts
supersedes
related_to

等。

ただし関係語彙について既存正本がある場合はそれを優先する。新しいrelation taxonomyを先に発明しない。

---

## 11. 類似task統合

台帳・明細の重要な目的は、一件のtaskを記録することだけではない。

類似taskを横断することで、

その種類の依頼を処理するとき、通常どんな情報が必要になるのか

を学習する。

例えば同型task 100件について、

* SPECが97件で必要
* TESTが94件で必要
* authority確認が81件
* framework documentationが73件
* rollback情報が65件

だったなら、次回の同型taskではこれを事前テンプレートとして利用できる。

つまり経験から、

このtask typeにはこの明細群が必要

という構造を育てる。

---

## 12. 必要情報テンプレート

類似taskの蓄積から、将来的にはtask typeごとの情報テンプレートを生成する。

これは固定された人手作成フォームではない。

過去のtask群から、

* よく必要になる情報
* よく不足する情報
* 不足すると失敗しやすい情報
* よく使うsource
* よく使う試験
* よく起きるfinding
* 必要なauthority
* 完了時に必要になる証拠

を抽出して更新する。

このテンプレートがRRIの次回調査を改善する。

---

## 13. UIとの関係

UIは台帳・明細の単なる閲覧画面ではない。

ユーザーが、

* 元依頼
* 分割された明細
* 各明細の種別
* 勘定科目
* 調査済み情報
* 不足情報
* source/evidence
* 関連2DER ID
* 未解決事項
* 最終結果

を一つの流れとして確認できること。

また不足情報がある場合、

この情報が不足しています
調査しますか
ユーザーが入力しますか

という操作へ繋げられることが望ましい。

最終的には、

UIから依頼に関する知識がどう育っているかを見る

ことができる状態を目指す。

---

## 14. 現在の明細改善で先に調査すること

いま即座にschemaを追加しない。

まず現行2DER/RRIについて、以下を棚卸しする。

1. 現在の明細schema
2. 明細生成処理
3. 原文保持方法
4. source/evidence保存機能
5. 勘定科目付与
6. embedding利用
7. annotation
8. findingとの関係
9. task/item/artifact等との関連付け
10. 類似task検索
11. template/learning相当機能
12. UIから取得可能な情報
13. 明細を後から更新・追記する既存経路
14. 明細を読むconsumer
15. 明細情報がPLAN/RRI/回答へ再利用される経路

各項目を、

既に存在
部分的に存在
存在しない
UNVERIFIED

に分ける。

---

## 15. 今回の設計上の問い

今回の目的は、

「新しい明細schemaを作ること」ではない。

問いは、

現在の2DERに散在している明細・科目・調査・証拠・関連ID・類似task・再利用機能を、どのように一つのDetail Lifecycleとして接続すれば、本来想定していた台帳システムになるのか。

である。

この答えが出るまでは、局所的な欄追加を本実装へ入れない。
