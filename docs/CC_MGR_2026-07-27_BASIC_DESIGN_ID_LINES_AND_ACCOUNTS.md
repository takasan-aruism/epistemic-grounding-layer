## 1. 2つの次元を先に定義する（混ぜない）

| | **意図分類（RRI）** | **勘定科目（EGL）** |
|---|---|---|
| 答える問い | **いま、この依頼にどう応じるか** | **この作業は、どこに積み上がるか** |
| 時間軸 | **この turn 限り。消える。** | **永続。集計される。** |
| 値の性質 | 応じ方・呼ぶ機能 | 帳簿上の所属 |
| 決め直し | 次の turn で変わってよい | **振替（訂正）として記録される** |

**∴ 両者は独立である。片方から他方を自動導出しない**（Taka: 厳密には異なる）。**同じ明細が両方を持つ。**

---

## 2. ★基本設計の結論 — **1投稿 = 1 ID（伝票）＋ 複数の明細（サブID）**

**Taka の2択のうち「1 ID の中にサブID を持ち、明細ごとに勘定科目を設定する」を採る。** 複数の top-level ID には分割しない。

### 2-1. 理由（4つ）
1. **投稿は世界で1回起きた出来事である。** 発信元・時刻・原文は1つ。**分割すると「実際に何が届いたか」の記録が壊れる**（運用方針 §6-3「起きたことの記録」）。
2. **訂正の単位が要る。** 読み違えた時に直すのは**明細であって出来事ではない。** 伝票を作り直す運用は、履歴を偽装する。
3. **原文への追跡可能性。** 「Taka がこう言った」を逐語で復元できることは、我々の規律の土台である。**親 ID が原文を保持する。**
4. **母数が壊れない。** 本日われわれは母数の汚染で1日を失った。**出来事の数（ID）と内容の数（明細）を分けて数えられる形**にしておく。

### 2-2. 構造（案・命名は設計/監査が既存に合わせる）
```
REQUEST_ID（伝票 = 1投稿）
  ├ 原文（逐語）/ origin / 実 ts / conversation_id
  ├ ID 単位の判定 : 進むか・止まるか（1つだけ）
  └ LINE_ID（明細）× n
       ├ span      : 原文の文字範囲（★必須）
       ├ 意図分類  : 応じ方 / 呼ぶ機能（RRI）
       └ 勘定科目  : 帳簿上の所属（EGL・★凍結済 chart から選ぶ）
```

### 2-3. ★捏造を構造で止める2つの決定論チェック
- **明細は必ず原文の span を持つ。** **span を持たない明細は捏造であり、機械で弾ける。**
- **勘定科目は凍結済 chart に存在するものだけ。** **無い科目を作らない。** 該当が無ければ §4 の仮勘定へ。

## 3. ★どの単位で何を決めるか

| 単位 | 決めること | 理由 |
|---|---|---|
| **ID（伝票）** | **進むか / 止まるか（1つだけ）** | 返答は1人に1回返る。**turn の判断は1つしか無い。** |
| **明細（サブID）** | **何をするか（機能選別）／どの科目に記帳するか** | **明細ごとに違ってよい。**「実装して」＋「ついでに現状も教えて」は別の機能。 |

**これが Taka の「ID の単位において、それがなんといえるのか、を一意に縛る必要はない」の実装形である。**
**ID 単位では意味を1つに縛らない。縛るのは「進むか止まるか」だけ。**

### 3-1. 未決の1点（MGR の推奨つき・設計/監査が決める）
**明細の一部が止まり、一部が進める時にどうするか。**
- **MGR 推奨（thin）: 最初は「1つでも止まれば ID 全体を止める」。** 部分進行は記録が複雑になる。**ただし「止めた明細を名指しして」聞き返す**（今日の Build 7 で 3d の応答に理由が載るようになった延長）。
- **将来 部分進行が要ると判断したら、その時に設計する。** **今は入れない。**

## 4. ★★短文で意図が複数想定できる場合 — **「多重依頼」と「多義」を分ける**

**ここが Taka の言う「雑にしている」ところであり、本日の最大の失敗の再発点である。**

| | 例 | 扱い | 明細数 |
|---|---|---|---|
| **多重依頼（連言）** | 「A を直して、あと B も教えて」 | **明細を分ける** | **増える** |
| **多義（1つの依頼だが読み方が複数）** | 「これ直して」 | **明細は1つのまま。その明細が解釈候補を複数持つ** | **増えない** |

**★この2つを混同してはならない。** 本日われわれは、**多義の入力に一意の正解ラベルを強制し、擁護できる別解を不正解として数えた**（厳密一致 0.78 / 別解可 0.92）。**多義を明細に分けると、同じ誤りを構造として作り込むことになる。**

### 4-1. 多義の明細をどう記帳するか → **仮勘定（suspense）**
- **意図が確定しない明細は「仮勘定」に記帳する。** **推測で科目を決めない。空欄にもしない。**
- **確定したら振替（訂正）として記録する。** **いつ・何を根拠に確定したかが残る。**
- **利点**: 「まだ分からない」が**帳簿上の正規の状態**になる。**エラーでも欠損でもない。** Taka の「揺れているものに一意の正解を強制するのはテスト設計者が無能」に構造で応える形。
- **副次**: **仮勘定の滞留は、そのまま「我々が解けていない依頼」の一覧になる。** 数えられる。

## 5. 分解を誰がやるか（決定論と LLM の境界）

| 段 | 担い手 | 内容 |
|---|---|---|
| **1. 候補の切り出し** | **決定論** | 文・節の区切り、箇条書き、列挙標識（「また」「あと」「ついでに」）、命令形の数 |
| **2. 1依頼か2依頼かの判定** | **LLM（提案のみ）** | 「調べて直して」は1つか2つか等。**決定論で切れない所だけ。** |
| **3. 確定** | **決定論** | **span 検査**（原文に対応するか）／**科目の存在検査**（凍結 chart に在るか）／**未確定は仮勘定へ** |

- **LLM は提案する。確定は決定論が行う。**（運用方針 §5-1 の適用）
- **★LLM に「分けてよいか」を判断させる場所が新しい判断点である。** **そこに既知の弱点（無いものを在ることにする）が入る。** **span 必須がその防波堤になる。**
