## 1-2. ★RRI と 2DER の目的（Taka 逐語・2026-07-28 追加）
> **「RRIが何をやるのか？ という部分が置き去りになっているように感じたので、歯抜けになっていたと思う。まぁ、昔論じてるけど誰も覚えちゃいないし私も更新している部分がおおい。**
> **本来、雑なユーザの意図を元に、それを具体的内容に落としつつ、外部内部の情報を利用してユーザの目的そのものも具体化させ（あなたもそうだけど、ユーザはもっと適当）、最終的にユーザの望むものを提供する（DWはそのための実装を担う）**
> **つまり、会話で済むものなら会話で終わる。データが欲しいか、知識が欲しいか、ユーザは色々変わる。その辺をLLMを利用し、4軸７カテゴリや台帳の勘定科目システムを取り入れて合理的かつ効率的に管理するのが２DER」**

### 1-2-1. この節が §1 に足すもの（★MGR の読み・Taka の本文ではない）
1. **★RRI は「意図を読む」だけでなく「★目的そのものを具体化させる」。** **依頼を分類して流すのではなく、育てる。**
2. **★外部・内部の情報を使ってよい。** **不足を埋めるための取得は、RRI の仕事の一部である**（§3 の「不足情報を★暗黙に補完しない」と矛盾しない。**暗黙にやらず、根拠を残してやる**）。
3. **★会話で済むものは会話で終わる。** **∴ DW task を作ることは成功の指標ではない。**
4. **★ユーザが欲しいものは変わる**（データ／知識／実装）。**∴ 出口が複数ある。**
5. **★勘定科目システムは、2DER の中核として名指しされている。** **「あれば良いもの」ではない。**

## 2. RRI が保証する状態（逐語）
> **DWへ依頼を渡す時点で、少なくとも以下が揃っている。**
> * **依頼者と発話者**
> * **元の逐語**
> * **文脈**
> * **意図**
> * **曖昧さ、不足、矛盾**
> * **必要な前提情報**
> * **調査済み情報と根拠**
> * **未確認事項**
> * **実行目的**
> * **制約**
> * **完了条件**
> * **保存先や案件との関係**

## 3. 禁止事項（逐語）
> * **生の依頼文をそのままDWへ渡さない**
> * **台帳の直接参照で不足を補わない**
> * **4軸を生成せずに、LLMの直感だけで7戦略を選ばない**
> * **判断結果の根拠を保存せずに次工程へ進めない**
> * **不足情報を暗黙に補完しない**
> * **RRIを単なるルーターとして実装しない**
