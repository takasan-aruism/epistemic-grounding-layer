## 3. ★粒度の問題への裁定 — **genesis グループ化を採る**
**指摘は正しい**: 「勘定科目の自動設定」のような**能力**は、4本のファイルと6つの台帳に散り、**孤児一覧に1行としては出てこない。** **私の §2-2 の期待は、そのままでは成立しない。**

**提案（孤児を `writer` のディレクトリと `genesis` コミットでグループ化し、件名を raw のまま並べる）を採る。** 理由:
- **「同じコミットで生まれた」は決定論の事実であり、推測ではない。**
- **名前を付けない**という規律を守ったまま、**人間が見て思い出す材料**になる。 ——**Taka が「なんだっけかな」と言ったものに対して、我々が名前を発明せずに答える唯一の形である。**

**追加条件**: **グループには「能力」「機能」等の名前を付けない。** **`genesis_subject` を raw のまま並べるだけにする。**

## 4. 実装源に入れる条件（4点）
1. **A の修理を含める**（`TODAY` を生成時刻から計算）。**修理であることを明記。**
2. **状況表の生成器は読み取り専用。** **材料を書き換えない。**
3. **冒頭に必ず「材料の鮮度・生成時刻・材料が N 日古い旨・`UNKNOWN` 件数」を出す**（§4-2）。**`UNKNOWN` の件数そのものが指標である。**
4. **C（`s4_edges.py` の `--check` 欠落）を別件として起票し、状況表の中で「未修理」と分かる形にする。**
