## 2. 設計（thin・1本だけ通す）
### 2-1. 通す1本
> **次の1件の本線作業を、`/api/submit`（または CLI）から投入し、返ってきた routing に従って進める。**

```
CC-α（設計/監査）が指示文を作る
   ↓  ★ここを変える: ファイルに直接書くのでなく front door へ投入
POST /api/submit  {"raw": "<指示文>"}          … または  python3 twoder/submit.py "<指示文>"
   ↓
submit() が返す TRACE:
   RRI_REQUEST_TYPE / RRI_PREFLIGHT / INTENT_STRATEGY / DISPATCH_RESULT / DW_TASK_ID
   ↓
★ Claude は TRACE の routing に従う（自分で決め直さない）
   ↓
BUILT / FINDING は従来どおり egl/docs（記録の経路は変えない）
```

### 2-2. 「従う」の定義（★ここが本体・曖昧にしない）
**「従う」とは、以下を守ることである:**
1. **`DW_TASK_ID` が返ったら、その task を作業単位とする**（自分で別の単位を切らない）。
2. **`RRI_PREFLIGHT` が `blocks_dw_escalation=True` を返したら、進まない**（Claude の判断で押し通さない）。
3. **`DISPATCH_RESULT` が示す先と違うことをしない。**
4. **返された routing が我々の意図と食い違った場合、書き換えずに「食い違った」と記録して MGR へ上げる。** **← これが最も重要。** 食い違いを潰すと、移行したことにならない。

### 2-3. 何を変えないか（作り直さない）
- **`submit()` を変更しない。** 投入するだけ。
- **記録の経路（`egl/docs` の CC_* 往復）を変えない。** 通信規約は不変。
- **意図調べ（段3e）の未動作（I-5）は本件と独立。** **3e が候補ゼロでも MIGRATION-3 は成立する**（routing は段4 が決めており 3e に依存しない）。**待たない。**

## 4. 完走の判定（条件3・先に決める）
**「本線作業が1つ完走した」と言ってよいのは、次が全部そろった時のみ:**
1. **指示文が `submit()` を通った**（TRACE が記録に残っている）。
2. **返された routing に従って作業した**（従った証跡が BUILT/FINDING に書かれている）。
3. **設計→実装→監査→commit が終わっている。**
4. **食い違いがあった場合、それが潰されずに記録されている。**

**1つでも欠けたら「完走した」と言わない。** **特に4を欠くと「従った」の証拠にならない。**
