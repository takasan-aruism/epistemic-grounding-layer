## 0. 結論
**D-21 の中核設計（`doc_id` が登記と同一計算＝退役時に付け替え不要）が、私の入力によって壊れている。**
**原因は IMPL の実装ではない。私の設計が2つの表記を混ぜていた。**

---

## 1. ★何が起きたか【監査:CC-α・実測】
```
再現: python3 -c "import cc_register as R; print(R.doc_id_for('egl/docs/X.md'), R.doc_id_for('docs/X.md'))"
  doc_id_for('egl/docs/X.md') = ART-318cd62f3f     ← 私が渡した形
  doc_id_for('docs/X.md')     = ART-c44e3f0065     ← artifact_registry と一致する形
```
`artifact_registry.artifact_id_for(repo_name, relative_path)` は **`sha1(repo + "|" + relative_path)`**。
**∴ `relative_path` は repo 相対（`docs/CC_x.md`）でなければならない。**
**私は `egl/docs/CC_x.md` を渡した。** **∴ `sha1("egl|egl/docs/...")` という、登記と一致しない id が14行分できた。**

## 2. ★原因は私の設計の内部矛盾（IMPL は仕様どおり）
**私の D-21 設計は、行の形をこう書いた:**
```
{"kind":"DOC","doc_id":"ART-xxxxxxxx","path":"egl/docs/CC_....md", ...}
```
**`path` を repo 接頭辞つきで例示しながら、`doc_id` は repo 相対から計算する式を指定していた。**
**∴ 1つの文書の中に2つの表記が並んでいた。** **変換の指示も書いていない。**
**∴ 私自身がその2つを取り違えて `path` を `doc_id_for` に渡した。**

**IMPL は `doc_id_for` を `artifact_registry` に実読で合わせている**（`[:10]` の件）。**実装は正しい。**

## 3. 修正案（膨らませない・v1.9）
### 3-1. 表記を1つにする（推奨）
> **`path` を repo 相対（`docs/CC_....md`）に統一する。** **`artifact_registry.relative_path` と同じ意味にする。**
> **∴ `doc_id_for(path)` が構造的に正しくなる。変換が要らなくなる。**

### 3-2. `record_doc` が受け付けないようにする（再発防止・小さい）
> **`record_doc` は `path` が `docs/` で始まらなければ `ValueError`。**
- **廃止するもの**: 無い。**ただしこれは「膨張」ではなく、台帳の中核性質（id 互換）を守る検査である。**
- **v1.9 の判定**: **足す理由は「無いと中核設計が静かに壊れる」。** **本日それが実際に起きた。**

### 3-3. 既存14行の扱い（★二重登録しない）
- **追記のみなので消せない。** **正しい id で入れ直すと `DOC` 行が倍になり、ずれ検出の分母が汚れる。**
- **∴ 入れ直さない。** **`path` は読める形で残っており、退役時の移行は `egl/` を剥がして再計算すれば復元できる。**
- **★退役条件に1行足す**: **「移行時、`path` が `egl/` で始まる行は接頭辞を剥がして `doc_id` を再計算する」。**
- **∴ 損害は復元可能である。** **隠さずに記録する。**
