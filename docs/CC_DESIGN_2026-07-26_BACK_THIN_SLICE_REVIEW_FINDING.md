## 1. ★内部矛盾: 「dogfood＝我々の開発依頼」と「④長文軸は defer」は両立しない
- §0 で長文軸を defer しつつ、§2-A で入力を**我々の開発依頼**にしている。**我々の開発依頼は一行ではない**（Taka の指示も MGR の本 DRAFT も段落単位）。
- ＝**縦串を流した瞬間に、未検証の長文領域に入る。**
- しかもそこは**既知の最大弱点が最も強く出る領域**: Qwen は「**主張された文脈を検証せず受け入れる**」（DE-0545）。長文入力とは**大量の"主張された文脈"を丸ごと渡すこと**に他ならない。
- **推奨: defer を解くのではなく、"長文で走ることを認めた上で必ず計測する"。**
  - 各 run に **入力長・意図調べの結果・崩れたか**を記録し、**崩れを長文起因と切り分けられる**ようにする。
  - 縦串の目的が「**壊れる所＝次に作る所**」なら、**長文で壊れるのは最も価値ある情報**である。**黙って走らせて "縦串が動いた/動かない" だけ見るのが最悪**。
  - slice1 を短文実依頼に限定する案もあるが、**dogfood の意味が薄れる**ので非推奨。

## 2. ★目的未達: 「後者が前者のバーを決める」が設計に入っていない
- §3 に「前者の実際に必要な精度がここで初めて分かる」とあるが、**それを測る仕掛けが無い**。正常系を1本流すだけでは「必要精度」は絶対に出ない。
- **必要精度は「意図を間違えた時に下流がどうなるか」でしか測れない。**
- **追加すべき（最小）**: **意図を故意に誤らせた注入試験**。
  - 例: 正しくは CONTEXT_RESOLVE の依頼に **BMV を強制**して RETRIEVE を走らせ、**返ってくるものが実用上壊れるか**を見る。
  - 近縁の取り違え（CONTEXT_RESOLVE↔BMV、INTENT_PROBE↔PREMISE_PROBE）は**下流が同じなら精度は要らない**。**遠い取り違え**（DIRECT↔DEFER）だけが致命なら、前者に必要なのは 0.9 ではなく「**遠い取り違えをしないこと**」になる。
  - ＝**これが入ると「0.71 で十分か」に初めて答えが出る。入らないと縦串は目的を果たさない。**
- 併せて **§1 の別解判定基準（「どちらを選んでも応答が実質同じなら別解」）が、ここで実測により検証できる**。今は私の判断でしかない。

## 3. ★第2メニューは手で書かない — LIVE 裏付けを必須フィールドにする
MGR 自身が「網羅性＝最重要・穴が開きやすい」と自己申告している通り。**手書きだと "できるつもり" を並べてしまう。**実データ:
- `structure/EDGE_INVENTORY.jsonl` 全 **1313 edge** のうち **LIVE は 113 のみ（8.6%）**。
- **IMPLEMENTED_UNWIRED 362 / TEST_ONLY_ISLAND 812 / WIRED_UNENTERED 9 / WIRED_EXECUTION_UNRESOLVED 17。**
- ＝**「実装されているが繋がっていない」ものが LIVE の3倍以上ある。メニューが未接続能力を約束する危険は高い。**

**是正: 各メニュー項目に「裏付けとなる LIVE callee_symbol」を必須フィールドとし、`--check` が EDGE_INVENTORY で LIVE 検証する**（LIVE でない項目をメニューに載せたら RED）。
なお DRAFT の候補は**実際に LIVE 裏付けがある**（手書きが当たっていた）:

| メニュー候補 | LIVE 裏付け（callee_symbol） |
|---|---|
| 登録 | `admit_design_evidence` (LIVE 3) |
| 実装準備 | `create_task` (2) / `record_plan` (2) |
| 現状観測 | `derive_state` (4) / `_read_events` (6) |
| 会話 | `record_dialogue_event` (3) / `record_utterance` (2) |
| 検索(retrieve) | `acquire` (3) |

→ **メニューは「あるべき能力」でなく「LIVE な能力」から作る。** これで網羅性の穴が"意見"でなく"機械の検証対象"になる。

## 4. probe→STOP→再開 は周辺の穴ではなく本丸（優先度を上げよ）
- §5 で「DS 連携未設計」と周辺扱いだが、**ここは既知の最大弱点が直撃する場所**。
- **ユーザーの返答＝「主張された文脈」**である。DE-0545 で Qwen は「文脈から明らかでは？」という**偽の主張に検証なく方針転換**した。
- ＝**聞き返して返答を受け取る経路は、我々が最も弱いと分かっている経路。** 「聞き返せば安全」ではない。
- **最小の防御**: 再開時、ユーザー返答を**そのまま文脈として信じない**。返答を**新しい依頼として再度意図調べにかける**（＝主張を検証せず飲む経路を作らない）。thin でもこれは削らない方がよい。

## 5. NOT_BUILT / BLOCK の記録は「オプション」でなく必須
- §5 で「残すか」と問うているが、**残す一択**。
- Taka の直近判定（過去引き＝あり／後から直させる＝なし）と 2DER の実績（**failure-history retention が実際に効いた唯一の線**）より、**stub が NOT_BUILT を返した記録・BLOCK した記録こそが将来の retention 資産**である。
- 「まだ作っていない」という事実の蓄積が、次に何を作るべきかを決める。**捨てたら縦串を回す意味が半減する。**

## 6. NO_ACTION の扱い（§5 の自己申告に回答）
- 前者の `NO_CANDIDATE` と**同型の穴が必ず出る**（実測: 相対選別で 3/63、独立選別で 14/63）。
- **捏造で埋めない**のは前者と同じ。ただし**前者と違い、後者の NO_ACTION は "2DER にその能力が無い" ことの証拠**になる。
- **NO_ACTION は失敗でなく発見として記録する**（§5 の retention 資産と同じ扱い）。

## 7. scope の線引き（Taka 判断用の私の意見）
- **過剰ではない。** むしろ §2 の注入試験を入れないと**過小**（目的を果たさない）。
