## 0. ★まず読んだ（作り直さないため）— 作らなくてよいものが2つ見つかった
**【監査:CC-α】`twoder/submit.py` の段構成を実読した:**
```
1  DS 記録
2  RRI context_binding.bind_context      ← ★既に LIVE
3a EGL grounding pass
3b RRI request_type.classify_request_type ← ★既に LIVE
3c DEAD-APPROACH ガード
3d RRI PREFLIGHT GATE                     ← 我々が Build 1 で触った段
4  ROUTING
```

### 0-1. ★事実の供給源は既に在る（新規に作らない）
`rri/rri/context_binding.py::bind_context` は **front door の段2 で毎回走っており**、返り値に:
- **`context_mode`**（`PROVISIONAL` / `DIALOGUE_STATE`）
- **`anchoring`**: **`UNRESOLVED`（文脈自体が無い）/ `LOW`（支配的な文脈が無い）/ `MEDIUM` / `HIGH`**
- `supporting_context_refs` / `residual`

**＝ Build 5 で我々が研究スクリプト内に作った「直前の文脈は記録に存在しない」という事実は、本番では `anchoring == "UNRESOLVED"` として既に出ている。**
**∴ 事実の生成器を新しく作る必要はない。既にある出力を文にするだけである。**

### 0-2. ★`request_type` と意図調べは重複していない（両方要る）
| | 何を分類するか | 値 |
|---|---|---|
| `request_type`（段3b・LIVE） | **何をしてほしいか** | `OBSERVE_CURRENT_STATE` / `BUILD_CAPABILITY` / `MODIFY_EXISTING` / `RESUME_PRIOR` / `DECIDE` / `OTHER` |
| 意図調べ（研究のみ・未配線） | **どう応じるか** | `DIRECT` / `CONTEXT_RESOLVE` / `CHOICE` / `BMV` / `INTENT_PROBE` / `PREMISE_PROBE` / `DEFER` |

**別の軸である。**「実装してほしい（`BUILD_CAPABILITY`）」と「でも対象が曖昧だから聞き返す（`INTENT_PROBE`）」は同時に成立する。
**∴ 意図調べは `request_type` の置き換えではなく、その手前に置く「応じ方の決定」である。**

## 1. 配線（thin・1本だけ通す）
### 1-1. 置く場所
```
3b  request_type（既存）
3c  DEAD-APPROACH ガード（既存）
3d  PREFLIGHT GATE（既存）           ← ここで止まったら以降は走らない（既存挙動）
★3e 意図調べ（新規配線）             ← ここに置く
4   ROUTING（既存）
```
**理由**: **3d で止まる入力は、応じ方を決める必要が無い**（既に止まっている）。**3d を通過したものだけが「どう応じるか」の対象**である。**段4 の直前に置くことで、routing の入力に応じ方が乗る。**

### 1-2. 渡すもの（★段2 の出力をそのまま使う。新規計算しない）
| 事実 | 供給源（既存） | 出す条件（D-9） |
|---|---|---|
| `直前の文脈は記録に存在しない。` | 段2 `anchoring == "UNRESOLVED"` | **★指示語または過去参照がある時だけ** |
| `直前の文脈が記録にある: <本文>` | 段2 `anchoring in {HIGH, MEDIUM}` + `supporting_context_refs` | 常時 |
| `支配的な文脈が定まらない。` | 段2 `anchoring == "LOW"` | **★同上（関係する時だけ）** |
| `「<語>」が指す対象は記録から特定できない。` | 段2 の `residual` / P2 の束縛判定 | 指示語がある時 |
| `「<対象>」は記録に見つからない／判定できない／ある。` | 段3d 内の `existence_grounding` | 過去参照がある時 |

### 1-3. ★D-9 の中核 — 出し分けの規則（決定論・LLM 不使用）
```
指示語または過去参照が有る  → 文脈・接地の事実を出す
そのどちらも無い（自己完結） → 文脈の事実を出さない（無関係だから）
```
**根拠【監査:CC-α】**: Build 5 で 20 fixture 中 17 に「文脈が無い」を配った結果、**止まる率が 0.371 → 0.420 に寄り**、**自己完結した依頼（BV3 0.93→0.57 等）を壊した**。**無関係な事実を渡すと「何か足りない」と読まれる。**
**判定は P2 が既に持っている**（指示語の表層＋束縛先の有無）。**新規判定を作らない。**

## 2. 直叩きの閉塞（書き5箇所）
**閉塞 ＝ 直接呼出の削除ではなく、その書き込みに対応する「依頼」を front door に通すこと**（既裁定）。
**∴ 各箇所について、対応する依頼を先に言語化する。** 以下は**設計の提案であり、実装ではない**:

| 直叩き | 対応する依頼（案） | front door 上の型 |
|---|---|---|
| `live_worker_runtime.py:140` `admit_design_evidence` | 「この実行結果を開発根拠として登録する」 | 既存の **DE admission fast path**（段1.5・**既に在る**） |
| `runtime_supervisor.py:218` `admit_design_evidence` | 同上 | 同上 |
| `webui.py:315` `record_plan` | 「この計画を記録する」 | **【未確認】対応する型が無い可能性** |
| `build_planner.py:301` `record_plan` | 同上 | 同上 |
| `experiment_candidate.py:116` `create_task` | 「この候補をタスクとして起こす」 | 段4 ROUTING → DW（**既に在る**） |

**★feasibility-first**: **`record_plan` 2箇所に対応する依頼の型が front door に無い可能性がある。**
- **原因**: front door は「依頼 → 分類 → 振り分け → タスク生成」であり、**「計画を記録する」は依頼ではなく内部工程**かもしれない。
- **3択**: (i) `record_plan` は内部工程として**閉塞対象から外す**（＝ orphan ではない と再判定する） / (ii) 「計画記録」の依頼型を新設する / (iii) 上級監査。
- **【設計:CC-α】私は (i) を推す。** **`record_plan` は タスクが既に在る前提での内部記録**であり、**上流に依頼が無いのではなく、上流の依頼は既にタスク生成時に通っている**可能性が高い。**ただし未確認であり、確認してから決めるべきである。**
- **∴ 閉塞の対象は、確認が済むまで `admit_design_evidence` 2 + `create_task` 1 の3箇所に絞ることを提案する。**

## 3. D-6（1問い合わせ = 複数明細）との関係（1段落・MGR 指示）
**同じ入口の話である。** front door は現在 **1つの `raw_input` → 1つの分類 → 1つの routing** であり、**複数明細を扱う構造になっていない。** Taka の指摘（長文は複数の依頼の集合）を入れるなら、**段3b/3e が「1つの答え」でなく「明細ごとの答え」を返す形に変わる**。
**ただし本設計では扱わない。** 理由: **(a) 明細への分解を誰がやるか（決定論か LLM か）が未決** — LLM なら新しい判断点であり既知の弱点が入る。**(b) account chart は完成・凍結につき触らない。** **(c) 1本の配線を通すのが先**（thin）。
**∴ 本設計は「1問い合わせ = 1明細」の前提で通し、複数明細は次の設計とする。この前提を明記して通す。**
