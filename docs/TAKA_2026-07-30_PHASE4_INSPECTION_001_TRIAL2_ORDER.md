## 目的

第1試行で確定した最初の停止原因、

**RUNTIME_INSPECTION経路の入口IDが既存の/api/resolveで解決できず、一つのIDから処理を追跡できない**

というID接続不全を一件だけ修正する。

修正後、同一のGPU情報取得依頼を再投入し、処理が次のどの工程まで進むかを確認する。

今回の目的はGPU取得機能全体の完成ではない。

最初の停止点を一つ修正した結果、E2E処理がどこまで前進したかを証拠付きで確定する。

## 1. 今回実施する修正

修正対象は一件だけとする。

**OBSERVE_CURRENT_STATE／RUNTIME_INSPECTION経路で応答に返されるtrace_keyを、既存の/api/resolveから解決可能にする。**

### 必須条件

修正後、trace_keyから最低限次へ到達できること。

* 受理された入力内容
* 受理時刻
* RRI判定
* runtime inspection実行記録
* 取得されたobservation参照
* 最終応答参照

現在のデータ構造上、一部が別IDになっている場合は、trace_keyから参照IDを辿れる形でよい。

### 禁止

* 新しい台帳を作らない
* 新しいresolve APIを作らない
* 今回専用のGPU分岐を作らない
* GPU取得コマンドを変更しない
* utilization.gpuを追加しない
* プロセスのGPU紐付けを追加しない
* DW task生成方式を変更しない
* Plannerを新設または強制起動しない
* 生出力の要約処理を追加しない
* 第1試行で判明した複数の問題を同時に修正しない

既存/api/resolveと既存ID体系の中で接続する。


## 3. 実装条件

### 最小差分

既存のtrace_keyを既存resolve機構へ接続するために必要な最小差分だけを実装する。

望ましい方向は、以下のどちらかである。

* trace_keyを既存イベントまたは記録の正式ID／aliasとして登録する
* trace_keyから既存の正典record ID群へ決定論的に解決する

どちらを採用するかは、現在の正典・ID設計との整合性で決める。

### Fail-closed

以下の場合は解決成功にしてはならない。

* 同一trace_keyが複数の無関係な要求へ対応する
* 入力内容が取得できない
* 親子関係が確認できない
* 参照先が存在しない
* ID形式だけ合っていて実体がない
* 時刻やrequestとの対応が曖昧

### 後方互換

既存の次の解決を壊してはならない。

* ARUN-*
* OBS-*
* SRC-*
* その他現在/api/resolveが正式対応しているID

## 4. 実装後テスト

同一E2E再検査の前に、今回の修正だけを確認する。

### 必須テスト

1. 既存のresolve対象IDが従来どおり解決できる
2. 未知のtrace_keyは解決失敗になる
3. 実在するRUNTIME_INSPECTIONのtrace_keyが解決できる
4. 解決結果から入力内容を取得できる
5. 解決結果からRRI記録へ到達できる
6. 解決結果からARUN／OBS参照へ到達できる
7. 別requestの記録が混入しない
8. 同一requestを再解決して結果が変わらない

テスト専用の偽成功データだけで終わらせず、過去の第1試行記録を利用できる場合は、SUBMIT-zOlryQでも確認する。

ただし、過去記録の構造上どうしても後付け解決できない場合は、その理由を明記し、新規試行でのみ検証する。
