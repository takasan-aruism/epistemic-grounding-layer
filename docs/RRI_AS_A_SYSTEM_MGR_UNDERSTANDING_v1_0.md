# MGR の現在の理解 — **RRI は「処理」か「系」か** v1.0

- **典拠**: Taka の問い（2026-07-28）「現在あなたが想定している RRI は、どこまでを内部に含む設計なのか」
- **★これは MGR の理解であって、正典ではない。** **正典は `RRI_CANONICAL_SPEC_v1_0.md`（Taka 逐語）である。**
- **★根拠はすべて本日の実測である。** **記憶で書いていない。** **未定義は「未定義」と書いた。**

## 0. ★結論（一行）
> **RRI は「系」である。ただし実装は、系として動くべきものが★段の直列として書かれている状態にある。**

## 1. RRI の責務
**持つもの（根拠は本日の実測）**
| # | 責務 | 根拠 |
|---|---|---|
| 1 | 発話が何の要求かを決める | `request_type`（6分類）が本番で走る |
| 2 | 何の話の続きかを結びつける | `context_binding.bind_context` が `context_anchoring` を生む |
| 3 | 出口（戦略）を選ぶ | `intent_strategy` が7戦略から1つ選ぶ |
| 4 | 具体化のために情報取得を要求する | `research_intent` / `research_signal` |
| 5 | 解けていない残りを更新する | `residual_update` |
| 6 | 判断の根拠を自分の台帳に残す | `intent_record.mint`（RRI 台帳の唯一の書き手） |

**持たないもの**: 実装（DW）／発話の記録（DS `record_utterance`）／設計根拠の正典（EGL `de_admission`）／取得の実行そのもの（取得系）／承認（`authority`・Taka）

## 2. 内部構造 — ★複数状態・複数判断を持つ系である
1. **判断が複数あり、別々の関数に分かれ、独立に成否を持つ。**
2. **★系に属していながら実行されていない判断が実在する**（`request_resolution.select_strategy` は入口条件が既定で偽）。**単一処理なら「在るのに通らない」は起こらない。**
3. **出口が複数ある**（会話で終わる／データ／知識／実装）。**単一処理は出口を持たない。**

**★ただし実装は系になりきっていない:** 現状は段の直列であり、状態を持つのは DW 側。RRI 側の状態は `intent_record` と `residual` に断片的に在るだけ。
**★未定義**: RRI が自分の状態機械を持つのか。持つならどこに置くのか。

## 3. Event Trace との関係 — ★外部から観測する設計である
> **Event Trace は「RRI が台帳に書いた事実」を記録する。「RRI が何を考えたか」は記録しない。**
```
合流点② = rri/intent_record の唯一の書き手
本日の実 run（21件）のうち RRI の event は "mint" ★1件だけ
分類結果・戦略選択・4軸の値は Event Trace に★1件も載っていない
```
**∴ 現在の Event Trace は RRI を「箱」として外から見ている。** **★これは意図した設計である**（責務点＝各台帳の唯一の書き手）。
**★帰結**: 「RRI がなぜその出口を選んだか」は Event Trace からは分からない。

## 4. 実行経路と系 — 混同していない証拠
| | 実行経路 | RRI という系 |
|---|---|---|
| 何か | `submit()` の段の並び（プロセス上の順序） | 要求を育てる責任範囲 |
| 持つもの | 分岐・早期 return・実行順 | 判断・状態・出口 |
| 観測 | Event Trace で追える | **★現状は追えない** |

**証拠A（系に在って経路に無い）**: `request_resolution.select_strategy` は RRI の設計要素だが実行経路に入っていない。**経路＝系ならこれは在り得ない。**
**証拠B（経路が短絡しても系は判断している）**: DE 登録依頼は段1.5 で早期 return する（経路3件）が、そこで「これは DE 登録である」という RRI の判断が下されている。**経路の長さと系の働きは一致しない。**

## 5. 将来拡張
**Phase 1 で固定する（もう動かさない）**
1. RRI の台帳の唯一の書き手は `intent_record` である
2. Event Trace の責務点は「各台帳の唯一の書き手」である（呼び手ごとに増やさない）
3. RRI が DW へ渡す時点で12項目を揃えるという目標（正典 §2）

**Phase 2 以降に追加されうる**: 4軸の生成（★3軸は本番に実装が無い）／決定論の戦略選択の配線／勘定科目の自動付与／不足情報の取得ループ／会話で終わる出口の明示

**★未定義（MGR が答えを持たない）**: RRI の「1件の依頼が終わった」の定義／再入の扱い／RRI が状態を持つか・持つならどこか
