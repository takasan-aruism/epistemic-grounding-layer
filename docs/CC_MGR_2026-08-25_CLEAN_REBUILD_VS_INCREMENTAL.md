### 4-1 クリーンリビルドで新規に書く必要がある箇所（★7箇所）

1. `_load_chart` を **LEGACY と現行に分ける**読み口（fail-closed の意味が変わる）
2. `account_gate._menu()` から **LEGACY を除く**（★段2の一覧が変わる＝LLM の挙動が変わる）
3. `account_gate.decide`(段1) の軸を **`AX-` から新体系へ**（★`frozen_direction` を作り直す＝別の生成器が要る）
4. `plan_backfill` の割当条件を **LEGACY 除外**へ

★**5 が最大**：921件の再投影は「履歴として保持しつつ現行判定から除外」を成立させるための書き込みで、

### 4-2 未分類率が確定できない理由（★推測で数字を置かない）

クリーンリビルド後の鍵Bは **69科目を全部採用した場合** に:

```
被覆される明細 803 → うち いま科目が無いもの が新体系で載る
被覆されない明細 1,186 − 803 = ★383   ← ★提案が無い ∴ どの体系でも載らない
```

∴ **鍵B の下限は 383/1,186 = 32.3%** ―― ★**いまの 22.3% より悪化する**。
★理由：現行は `AX-` が254件、`ACC-` が11件を抱えており、**それらを LEGACY にすると 265件が未分類へ戻る**。
★**「載っていた明細が載らなくなる」** のが、この案の最大の代償。

★但し **再投影（4-1 の5）が成功すれば** 265件は新科目へ移せる ∴ 最終的な鍵Bは 383 に近づく。
★**再投影が成功する保証は無い**（803被覆に 265件が含まれるかは corpus 次第）＝ ★**未測**。

## 5. ★所見（数字から言えること）

1. **「増分方式が壊れている」わけではない** ―― ID churn 0・不動点 GREEN・既存参照破断0 は実測で出ている。
   今日の閊えは **上流（生成器・命名台帳）を走らせていないこと** であって、方式の欠陥ではない。
2. **クリーンリビルドの代償が大きい** ―― 既存参照破断 **921件**・人手裁定 **69件**・実装 **7箇所**・
   ★**鍵Bはむしろ悪化する**（22.3% → 下限32.3%）。
3. **★本当の問題は別の場所にある** ―― 未分類の最大原因は
   `PROPOSE_ACCOUNT_ABSENT 374`（★提案が無い）で、これは **科目体系をどう作っても消えない**。
   体系を作り直しても、**提案が無い明細は依然として載らない**。
4. **世代の混在で実害が出ているのは1点** ―― **段1（決定論）が `AX-` 世代の軸しか見ていない**。
   ★ここだけは体系を作り直さなくても直せる（★`LDET-` 側の `frozen_direction` を作る＝生成器1本）。
