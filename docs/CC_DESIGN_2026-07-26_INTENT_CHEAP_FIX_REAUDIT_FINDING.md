## 4. ★★文脈の捏造 — 3度目の目撃（本 finding の最重要）
IP1「あれ、どこにあったっけ？」IP2「それ、その後どうなった？」は**いずれも `context=""`（文脈は空）**。にもかかわらず:
- IP1 = [INTENT_PROBE, **CONTEXT_RESOLVE**, PREMISE_PROBE]
- IP2 = [**CONTEXT_RESOLVE**, PREMISE_PROBE, PREMISE_PROBE]

**`CONTEXT_RESOLVE` = 「直前の文脈に支配的な解釈があり文脈で絞れる」。文脈が空なのだから、構造的にあり得ない選択である。**

これで同じ弱点の目撃が **3件（独立）**:
1. **DE-0545**: 文脈が空なのに「文脈から明らかでは？」と偽の主張を置いたら、**検証せず方針転換した**。
2. **arm-C3 CH2**: 文脈が空なのに「**前回の会話で目的地や日程が既に話されている**」と**存在しない会話を捏造**した。
3. **本件**: 文脈が空なのに **CONTEXT_RESOLVE を選んだ**。

→ **これは偶発ではなく、この model の一貫した性質である。** そして **2DER の front door は「前提を確認する」ことが根幹**なので、**ここが最大のリスク**。

### ★即効の是正（決定論・LLM 不要・安く確実）
**`context` が空なら `CONTEXT_RESOLVE` を候補から機械的に除外する。**
- 「文脈で絞れる」は**文脈の存在が前提条件**であり、**前提が無いことは機械が知っている**。LLM に判断させる必要が一切ない。
- Taka が承認した「空入力は入口で機械的に弾く」と**同じ family の手当て**（前提が構造的に成立しない選択肢を、LLM に触らせない）。
- **これは §2 の DEFER 是正と違い、因果が構造的に保証されている**（ノイズではない）。IP1 seed1・IP2 seed0 の 2 件は確実に消える。
- **一般化**: 各戦略の**前提条件を宣言し、成立しないものは候補から機械除外**する（例: `CONTEXT_RESOLVE` requires `context != ""`）。**これは MUTEX 規則2（正解を削って有害だった）とは別物** — あれは「意味的に排他だろう」という推測だったが、こちらは**構造的に判定可能な前提**である。

## 5. その他の確認

## 6. 提案
1. **`CONTEXT_RESOLVE` の前提条件（context 非空）を機械で強制**（§4）。**次イテの最優先**。因果が構造的なので測る前から効くことが分かっている数少ない手当て。
2. **戦略ごとの前提条件を宣言する仕組み**に一般化（宣言は事前固定・記録・`--check` で検証）。
3. **指示語系（IP1/IP2/IP3）は定義整理では解けない**ことが判明したので、**別アプローチが要る**（例: 指示語検出は決定論で可能——「あれ/それ/例の」等——し、検出したら INTENT_PROBE を**強制候補**にする）。**これも LLM でなく機械の仕事。**
4. 縦串は予定どおり着手可（本 fix で NO_CANDIDATE=0 になり、常に routing 先が決まる状態になった）。
