# PART 1 — メニュー制限（P3 の作り替え）

## 1. 何を変えるのか（一行）
**構造的に成立しない戦略を、メニューに載せない。** 現行は載せてから後で消している（後置フィルタ）。
**【監査:CC-α】現物確認**: `s_intent_role_split_d2p2.py::_rel_prompt` は `context` が空でも `STRAT_NAMES`（7つ）全部を提示している。

## 2. 各戦略に「成立の前提」を宣言する
**全7戦略について前提を1つずつ書く。書けないものは「前提なし」と明記する（無理に作らない）。**

| 戦略 | 成立の前提（案・IMPL は実装前に確認すること） |
|---|---|
| `CONTEXT_RESOLVE` | **`context` が非空**（定義が「直前の文脈に支配的な解釈があり」なので、文脈が無ければ定義上あり得ない） |
| `DIRECT` | 前提なし |
| `CHOICE` | 前提なし |
| `BOUNDED_MULTI_VIEW` | 前提なし |
| `INTENT_PROBE` | 前提なし |
| `PREMISE_PROBE` | 前提なし |
| `DEFER` | 前提なし |

- **前提は data（宣言）として持ち、記録する。** code に埋め込まない。**後から反証できる形にする。**
- **【設計:CC-α】「前提なし」が6つあるのは、いま構造で判定できるのが文脈だけだからである。** 増やしたい候補があれば**提案のみ**して DESIGN→Taka の承認を待つ（証拠なく前提を足すと、正しい選択肢を殺す）。

## 3. ★受入（3点を対で・片方だけなら採用しない）
1. **構造的不可能の証明** — **`context` が空の入力で、生成された prompt に `CONTEXT_RESOLVE` が含まれないこと。**
   - **★LLM を呼ばずに示せる。** prompt 文字列を生成して検査するだけ。**最初にこれを出すこと**（安い・決定的）。
2. **機能を殺していない** — **`context` が在る入力では従来どおりメニューに載り、選ばれ得ること**（`CR1`/`CR2`/`CR3` で確認）。
3. **★振り直しの有無** — 後置フィルタで `NO_CANDIDATE` に落ちた **7件**が、メニュー制限で**合法な選択肢に振り直されるか。**
   - **振り直されなければ「振り直されなかった」と書く。** **それも方式の限界の測定であり、失敗ではない。**
   - **【設計:CC-α】私は「振り直しが起きる」と予測している。予測が外れたら外れたと書かせる**（本日、私の予測は2回外れている）。

## 4. 測定の規律
- **対照設計**: 同一 fixture・**後置フィルタ arm vs メニュー制限 arm**。**ただし2アームで prompt が違うので LLM 出力は共有できない。** ＝ **分布で出す（最低10 run・2バッチ）。**
- **主指標は遠隔取り違え率**（`STOP={INTENT_PROBE,PREMISE_PROBE,DEFER}` / `ACT={DIRECT,CONTEXT_RESOLVE,CHOICE,BMV}` の境界を跨ぐ誤り・**分岐点から機械導出**）。**一致率は M2 として併記継続。**
- **`BROKEN-UNSAFE` と `BROKEN-WASTEFUL` を必ず分ける。**
- **`NO_CANDIDATE` は誤答と同列に数えない。** 別枠。

## 5. `_rel_prompt` の他の前提も洗う（MGR §2）
**各戦略の前提を書き出す作業の中で、`context` 以外に「構造的に不可能な選択肢を差し出していないか」を洗うこと。**
- **見つからなければ「見つからなかった」と書く。** 無理に作らない。

# PART 2 — 発話レコードの `origin` 欄

## 6. ★設計判断（MGR が私に委ねた点）: **(a) の続きとして同一スライスで行う**
**理由**:
1. **触る場所が同じ**（`record_utterance` / front door の呼び出し口）。**(a) で `ts_source` を足したのとまったく同じ形。**
2. **効果の帰属が混ざらない。** `origin` は**記録の追加**であって精度指標に影響しない。**本日の「まとめて出すと帰属できない」に該当しない。**
3. **同じ規律で書ける**（前向きのみ・遡及書き換えなし・推測で埋めない）。

## 7. 仕様
```
origin: HUMAN_DIRECT | HUMAN_RELAYED | MACHINE_SUBMIT | MACHINE_CODEGEN | UNSPECIFIED
```
- **★呼び手が申告する。推測しない。申告が無ければ `UNSPECIFIED`。**（**本日の原則。`ts_source` と同じ扱い。**）
- `HUMAN_RELAYED` の時は **`relayed_by`（誰が投入したか）と `authored_by`（誰が書いたか）を併記**する。**「直接打った」と偽らない。**
- **前向きのみ。過去 491件は `UNSPECIFIED` のまま。遡って推測で埋めない。**

## 8. ★MGR の「これがあれば除外フィルタは要らない」を訂正する【設計:CC-α】
**将来分については正しいが、全体としては誤り。**
- **過去 491件は永久に `UNSPECIFIED`** である（前向きのみだから）。
- **∴ 歴史データを扱う限り、除外フィルタは残さなければならない。** 消してはいけない。
- **正しい言い方**: **「`origin` が入った以降のレコードについては、除外フィルタでなく `origin` で判定する。それ以前は除外フィルタで判定する。両者の境界（最初に `origin` が入ったレコード id）を記録する。」**
- **【設計:CC-α】境界を記録しないと、後から「どこから信用できるか」が分からなくなる。** これも記録の規律である。

## 9. 受入（PART 2）
1. **既存 LIVE の非回帰**（`test_preflight_gate` 13/13・`ds` 系テスト・触った経路の既存テスト全て）。
2. **新規発話に `origin` が入ることを実証**（front door 経由＝`MACHINE_SUBMIT`）。
3. **申告が無ければ `UNSPECIFIED` になること**（推測しないことの実証）。
4. **既存レコードの差分ゼロ。**
5. **境界（最初に `origin` を持つレコード id）を記録に残す。**
6. **除外フィルタを消していないこと**（§8）。

## 11. feasibility-first（私が予見している困難）
- **(i) メニューを削ると、モデルが「該当なし」を返しやすくなる可能性がある。** 選択肢が減るので。**`NO_CANDIDATE` が増えたら、それは振り直しの失敗であり、正直に出すこと。**
- **(ii) `origin` の申告は呼び出し口ごとに要る。** front door 以外の `record_utterance` 経路が複数あるなら、**申告しない経路は `UNSPECIFIED` のままでよい**（無理に全経路を触らない・thin）。**触った経路と触っていない経路を列挙すること。**
- **(iii) PART 1 と PART 2 は独立に出してよい。** 分けるなら分けたと書く。**PART 1 の受入①（LLM を呼ばない証明）を最初に出すのが最も安い。**
