# CC 管理(MGR) → 設計/監査(CC-α): **★帳簿を直接読んで答えるのをやめる。システムに聞く**（方針変更・D-12/D-14 の出し方を差し替え）

- `BUILD_ROLE: 参照` / **宛: DESIGN/AUDIT(CC-α)** / 写: Taka / 発: MGR / 2026-07-27 / TYPE=HANDOFF
- **運用方針 確認済（版: v1.2 → 本文書で v1.3 へ改訂）**

## 0. Taka 直接発話（逐語）
> **「まぁ簡単な機能から確認していかないといけないわけだけど、あなたたちが帳簿を勝手に読んでいる間は一生変わらん。」**

## 1. MGR の理解（そして直前の私の誤り）
**私は D-12/D-14 で「帳簿を読んで事実を出せ」と指示した。** **それがまさに Taka の言う「勝手に読んでいる」である。**
- 我々が grep で答えを得ている限り、**システムは一度も「答える」経験をしない。** **機能が足りないことすら露見しない。**
- **我々が読めてしまうから、読み出し機能が無くても困らない。** **困らないから作られない。** ——**移行が進まない理由と同じ形である。**

## 2. ★方針（本日以降）
> **帳簿の中身に関する問いは、システムに聞いて答える。**
> **システムが答えられないなら、「答えられなかった」が結果である。それが次に作る機能そのものになる。**

### 2-1. 適用範囲（私の判断・設計/監査が詰める）
| 問いの種類 | 扱い |
|---|---|
| **帳簿の中身**（何が記帳されているか／科目は何か／この ID に何が在るか） | **★システムに聞く。** 直接 grep しない |
| **コードの構造**（どの関数がどこから呼ばれているか） | 直接読んでよい（**実装作業そのもの**） |
| **どちらか曖昧なもの** | **設計/監査が判断し、判断の理由を書く。** 迷ったら「システムに聞く」を選ぶ |

### 2-2. 例外の扱い
- **読み出し機能そのものを作る／直す作業**では、当然コードと記録を読む。**ただし「読んで得た答え」を成果として報告しない。**
- **どうしても直接読んだ場合は、`【直読】` と明記する。** **何回直読したかが、そのまま「機能が足りない」の数字になる。**

## 3. D-12 / D-14 の出し方を差し替える（作業自体は取り消さない）
**先に出した「帳簿を読んで事実を出せ」を撤回し、次に置き換える:**

1. **簡単な問いから、1つずつシステムに聞く。**（Taka: 「簡単な機能から確認していかないといけない」）
   - 例（順に）: **「この ID に何が記帳されているか」→「この ID の科目は何か」→「未確定のものは在るか」→「EXEC_ARCH は使われているか」**
   - **聞き方は front door 経由**（Build 8 で通す `submit` の CLI）。
2. **返ってきたものを逐語で記録する。** **返らなかったものは「返らなかった」と記録する。**
3. **その「返らなかった一覧」が差分表になる。** **＝ 差分表は、我々が読んで作るのではなく、システムに聞いて出来る。**
4. **【直読】した箇所は明記する。** 直読ゼロを目標にしない（今は無理）。**数えることが目的。**

## 4. Build 8 との関係（統合する）
**Build 8（MIGRATION-3 第1号）は「指示を投入する」だったが、本方針で「問いを投げて答えを得る」も同じ口を使う。**
- **設計/監査は、Build 8 の第1号に §3-1 の最初の問いを含めてよい**（分けるなら分けたと書く）。
- **食い違い・無応答は潰さず記録する**（既定どおり）。

## 5. 運用方針を v1.3 に改訂した
**§6-7 を追加:**
> **帳簿の中身に関する問いは、システムに聞いて答える。直接読んで答えない。**
> **システムが答えられないことは失敗ではなく、次に作る機能の発見である。**
> **やむを得ず直接読んだ場合は `【直読】` と明記する。直読の回数は「読み出し機能が足りない」ことの数字である。**
