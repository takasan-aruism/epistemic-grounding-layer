# finding: 状況表の台帳checkが6日前の値を「現在」として出していた

- 起票: CC_ALPHA(監視) 2026-08-24
- 宛先: MGR（★「計器の維持」は MGR の担当。私は直さず報告する）
- 種別: FINDING（計器の欠陥。★系そのものの欠陥ではない）

## 1. 何が起きていたか

状況表の1行 `台帳登記 check: 1 mismatch(es) over 56 ledgers` は **2026-08-18 04:09 の値**だった。
同じコマンドを 2026-08-24 に直接走らせた実測は **`0 mismatch(es) over 42 ledgers`**。

∴ **6日間、毎セッション「mismatch が1件ある」と表示し続けていた（真は0件）。**

## 2. 原因（実測）

| 事実 | 実測値 |
|---|---|
| 控えの最終更新 | `.claude/hooks/.2der_status_cache` = **2026-08-18 04:09** |
| `UserPromptSubmit` の呼び方 | `2der_status.sh brief` → **控えを読むだけ** |
| `SessionStart` の呼び方 | `2der_status.sh full` → **控えを書き直す** |
| `SessionStart` フックの timeout | **10 秒** |
| full が呼ぶ台帳check の所要 | **30.9 秒**（`egl/structure/s10_ledger_registry.py --check`） |

∴ **SessionStart は毎回 10秒で打ち切られ、控えを書き直せない。**
`brief` は打ち切られた事実を知らないので、**古い値を「現在」として出す**。

★これは「計器は系と同じ理由で壊れる」の再現：**止まったことが表示に出ない**。

## 3. 56 → 42 は欠損ではない（★私も一度そう疑った）

台帳が14本消えたのではなく、**意図的な統廃合**だった。

- `6ab2ff2` 台帳の統廃合 2: 登記簿の母数から実験の作業物を外す（**56 → 46**）
- `be4799b` 台帳の統廃合 1: 安全な2件だけ統合する（**46 → 41**）

∴ **失われた台帳は0本。** 分母が動いただけ。

## 4. 私がやったこと / やらなかったこと

- **やった**: 控えを1回だけ走らせて更新した（= 計器を「動かした」だけ。中身は変えていない）。
  更新後 = `0 mismatch(es) over 42 ledgers`。
- **やらなかった**: `2der_status.sh` も `settings.json` も直していない。
  ★理由 ①「計器の維持」は MGR の担当 ②両方とも **どのリポジトリにも入っていない**
  ∴ 直しても commit できず、次に消えても誰も気づかない。

## 5. 依頼（MGR）

**「控えが更新できなかった」ことが表示に出る形にする。**
値そのものより、**古い値を新しい値の顔で出さない**ことが要る。

候補（どれを採るかは MGR/Taka の判断）:
1. 重い台帳checkを SessionStart から外し、別に走らせて控えだけ読む。
2. 控えに書いた時刻を持たせ、**N時間以上古ければ「(古い: MM-DD HH:MM 時点)」を付けて出す**。
3. `SessionStart` の timeout を実測(30.9秒)より大きくする。

★併せて: `2der_status.sh` と `settings.json` が **版管理の外に在る**こと自体を扱うか、も判断が要る。

# 追記: 同じ計器で2件目 — 「Takaにしか出せない件」と「MGR未応答」が1つのリストに見える

## 6. 何が起きたか（2026-08-24 06:34 実測）

状況表の表示:

```
★Taka にしか出せない件: 34 件（我々の受入では埋まらない）
  - CC_MGR_2026-07-31_D188_WE_ARE_THE_TREADMILL.md
  - CC_MGR_2026-07-31_D190_PUSHING_DOES_NOT_HELP.md
  - CC_MGR_2026-08-23_DETAIL_LIFECYCLE_GAP_TABLE_v0.1.md

  - CC_ALPHA_2026-08-24_TASK_THREAD_BULK_READ_HANDOFF_v0.1.md   ← ★別のリスト
  - CC_ALPHA_2026-08-24_STATUS_CACHE_STALE_FINDING_v0.1.md      ← ★別のリスト
```

私はこれを見て「自分が渡し先を間違えた（MGR宛のつもりが Taka 宛になった）」と読んだ。**誤読だった。**

## 7. 実測（★鍵を分けて数え直した）

| 鍵 | 件数 | 中身 |
|---|---|---|
| `cc_register.pending('TAKA')` | **34** | 私の2件は **含まれない**（`False`） |
| `cc_register.pending('MGR')` | **2** | **ちょうど私の2件** |

∴ **渡し先は正しかった。** 表示だけが2つを1つに見せていた。

## 8. 原因（`2der_status.sh` の出力順）

- L223 `line "★Taka にしか出せない件: ..."` → L224 `TAKA_LIST`（**先頭4件だけ**）
- L226 `台帳のずれ` は **`full` のときだけ** ∴ `brief` では出ない＝**間に何も挟まらない**
- L228 `if PN != 0` → `PENDING`（MGR未応答）を**見出しなしで**印字

MGR未応答の見出しは **L79**（ずっと上）に在る。∴ 明細だけが遠く離れて印字され、
**直前の Taka リストの続きに見える。**
`TAKA_LIST` が4件で打ち切られていることも表示に出ないので、境目がさらに分からない。

## 9. なぜこれが効くのか

★この2つは **混ぜてはいけない2つの鍵**（`human` と `routed`）。
「Taka にしか出せない件」は**我々の受入では埋まらない**もの、
「MGR未応答」は**我々で片づく**もの。混ぜると **片づくものを Taka 待ちに見せる**。

★実害（実測）: 私自身が「自分が渡し先を間違えた」と判断しかけ、確認に手数を使った。

## 10. 依頼（MGR）

**見出しと明細を離さない。** 具体的には:
1. MGR未応答の明細を、その見出し（L79）の直下で印字する。
2. `TAKA_LIST` が先頭4件で打ち切られていることを表示に出す（`… 他30件`）。

★§5と同じ計器・同じ型（**止まったこと／打ち切ったことが表示に出ない**）∴ まとめて扱ってよい。

# 追記2: 3件目 —「front door から取れない」は1回の失敗を状態として断言している

## 11. 何が起きたか（2026-08-24 06:37 / 06:40）

状況表が2回続けて出した:

```
現在地: front door から取れない
実行中プロセス: ソースより新しい起動 or 該当なし
```

**入口は動いていた。** 同時刻の実測:

| 測ったもの | 結果 |
|---|---|
| `/api/tasks` | **3/3 成功**・0.4〜0.6秒・609件 |
| `/api/roadmap`（★この行が使う口） | **3/3 成功**・2.7〜3.1秒 |
| webui プロセス | **在る**（pid 2950852） |

## 12. 原因（`2der_status.sh` L270）

```
CURPOS=$(timeout 20 python3 - <<'PYEOF' 2>/dev/null || echo "現在地: front door から取れない")
```

**1回しか叩かない。失敗したら即その文言。**
`/api/roadmap` の実測は2.7〜3.1秒なので上限15秒には収まる。
∴ 06:37/06:40 の失敗は本物だが、**理由は「入口が落ちた」ではなく「webui が再起動中だった」**。

★実測: webui の pid は5分で **2948265 → 2949147 → 2950852** と3回替わっている
（別インスタンスが EVO-0101 で入口を並列化する作業中）。再起動の窓に当たれば接続は当然拒否される。

## 13. なぜこれが効くのか

★**同じ出力の最終行に規律が書いてある**:

> 規律: … **1回の観測で断定しない。**

**計器自身がその規律を破っている。**
「取れなかった」（測れなかった）と「落ちている」（測って不在だった）を分けていない。
★§5・§6 と同じ根: **止まった／打ち切った／取れなかった、が結論の顔で出る。**

★実害（実測）: 私は入口の障害を疑って切り分けに手数を使った。入口は健全だった。

## 14. 依頼（MGR）— §5・§10 とまとめて1件でよい

1. 1回失敗したら**もう1回だけ**叩く（間隔をあける）。2回とも駄目なら断言する。
2. 断言しないなら文言を**測れなかった側**にする:
   「現在地: 取れなかった（1回試行 / HH:MM）」。
3. `実行中プロセス: … or 該当なし` も同じ ―― **「該当なし」と「見に行けなかった」を分ける**。

★★3件とも同じ1行で直せる型: **計器は「測れなかった」を「測って無かった」と書かない。**
