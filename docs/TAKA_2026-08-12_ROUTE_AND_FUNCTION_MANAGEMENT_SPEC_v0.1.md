## 0. 目的

本仕様は、2DER内部の「経路表」を、人間が手で維持する静的な表ではなく、2DER自身の構造・機能・実行実績に応じて継続的に成長する管理システムへ移行するための設計を定める。

本システムは単なる経路一覧ではない。

2DERに存在する部品、部品間の接続、各部品の機能、実際の稼働実績を相互参照できる状態を作る。

Takaの表現では、

「人体図鑑のような物であると同時に機能表」

である。

最終的には2DER自身が、次の問いに自らの記録から答えられる状態を目標とする。

* 何が存在しているか
* 何と何が接続されているか
* その接続は処理経路なのか
* 各部品は何をするものか
* その機能はどこに存在するか
* その経路は実際に通ったことがあるか
* どこまでが確認済みで、どこからが未確認か

## 2. 基本原則

### 2.1 Managerは探索しない

経路候補や機能候補をManagerが人手で探してはならない。

Managerの役割は、

* 問い合わせる
* 状態を読む
* 必要な場合に承認する

ことであり、repo内を探索して接続関係を発見することではない。

探索作業をManagerへ戻す設計は失敗とする。

### 2.2 Worker LLMにも自由探索させない

Worker LLMへ、

「repoを読んで経路を探せ」

とは指示しない。

上位LLMであっても、repo全体から機能・経路・意図を一貫して発見する作業は不安定であり、同じ調査を繰り返す原因になる。

したがって、

機械が候補を作り、Workerは限定された候補について意味を分類する。

### 2.3 存在・意味・実績を分離する

経路を一種類の真偽値で扱ってはならない。

以下の3層を分離する。

**STATIC_EDGE**

コード上に接続が存在するという事実。

例：

AがBをimportしている。

AからBの関数が呼ばれている。

これは機械的に確定する。

**ROUTE_EDGE**

STATIC_EDGEのうち、2DERの処理経路として意味を持つもの。

これはWorker LLMによる分類対象とする。

**OBSERVED_EDGE**

実行時にその接続を実際にデータ・命令・状態が通過したことが記録されたもの。

これは実行記録によって確定する。

したがって、

「コード上で繋がっている」

「処理経路である」

「実際に通った」

は別の事実として保持する。

### 2.4 Workerは存在を発明しない

Worker LLMが新しい部品、新しい接続、新しい経路を自由記述して追加することは禁止する。

静的な接続の存在は機械が確定する。

経路としての意味はWorkerが分類する。

実際に通った事実は実行記録が確定する。

Workerはいずれの存在そのものも発明しない。

### 2.5 「無い」「判断不能」を正式な回答として扱う

LLMへ回答を強制しない。

全ての分類には、

* 一覧に無い
* 判断できない
* 近いものが無い

等の選択肢を持たせる。

不明状態を保持することは失敗ではない。

根拠なく分類することを失敗とする。

## 3. システム全体構造

本システムは3段階で構成する。

**段A：機械による候補生成**

既存コード・実行記録から接続候補を抽出する。

LLMは使用しない。

**段B：Worker LLMによる意味分類**

段Aで作られた限定候補について、Workerへメニュー形式で問い合わせる。

自由記述による発見は行わせない。

**段C：経路表・機能表への登録**

分類結果のうち、登録条件を満たしたものだけを正式な経路表・機能表へ反映する。

Worker自身は登録しない。

---

## 4. 管理する主要概念

最低限、以下の4概念を独立して保持する。

### 4.1 Component

実装上存在する部品。

例：

* module
* class
* function
* service
* endpoint
* worker
* scheduler
* ledger writer

Componentの存在はコードまたは既存台帳によって確認する。

### 4.2 Edge

Component間の静的な接続。

例：

A → B

Edgeには少なくとも以下を保持する。

* source component
* destination component
* 接続種別
* 発見方法
* source位置
* destination位置
* STATIC_EDGEの有無

### 4.3 Function

部品または経路が担う機能。

例：

* 受信
* 検証
* 分類
* 登記
* 配送
* 監査
* 実行
* rollback

Function名は既存一覧から選択する。

Workerが自由に新しい名称を作らない。

### 4.4 Evidence

接続・機能・経路についての根拠。

例：

* source上のimport
* call
* runtime log
* receipt
* ledger
* trace
* Worker判定
* 承認記録

## 5. 段A：機械による候補生成

### 5.1 目的

人間またはManagerがrepoを探索する作業を排除する。

機械は「意味」を決めない。

機械は観測可能な存在だけを列挙する。

### 5.2 抽出対象

最低限、以下を機械的に取得する。

* import
* from import
* function call
* class利用
* endpoint呼び出し
* subprocess
* shell呼び出し
* service呼び出し
* repo間参照
* 既存runtime記録

### 5.3 候補条件

抽出された接続のうち、既存経路表に正式登録されていないものを候補とする。

候補には少なくとも以下を付与する。

* source
* destination
* 接続の検出根拠
* source位置
* destination位置
* runtime evidence 有／無
* 送信記録 有／無
* 受信記録 有／無
* 同一repo／repo跨ぎ
* 既存経路表との重複 有／無

### 5.4 機械が確定してよいこと

機械が確定できるのは、

「コード上にAからBへの静的接続が観測された」

までとする。

以下は機械だけでは確定しない。

* 重要な処理経路か
* 単なるutility利用か
* 本番上の主要経路か
* 設計意図上どの機能に属するか

---

## 6. 候補の機械的整理

候補数が大量になることを前提とする。

LLMへ渡す前に、機械的特徴によって候補を分類・集計する。

最低限、以下を出力する。

* 候補総数
* 既存経路との重複数
* runtime evidenceあり
* runtime evidenceなし
* 同一repo内
* repo跨ぎ
* importのみ
* callあり
* 送信記録あり
* 受信記録あり
* 双方のruntime記録あり

候補の削減・優先順位づけにLLMを使用しなくても可能な特徴は、先に機械で処理する。

---

## 7. 段B：Worker LLMによる分類

Workerへ渡す問いは限定する。

自由な設計説明、推測、命名は求めない。

### 7.1 問い1：この接続は経路か

選択肢：

1. 経路である
2. ただの部品借りである
3. 判断できない

### 7.2 問い2：この部品は何をする所か

既存Function一覧から選択する。

追加選択肢として必ず、

「一覧に無い」

を置く。

### 7.3 問い3：この機能は既に在るか

既存Function一覧または既存類似機能から選択する。

追加選択肢として必ず、

「在る物の中に近い物は無い」

を置く。

---

## 8. Workerへ渡す情報

Workerにrepo全体を無制限に読ませない。

候補A→Bを分類する際、基本的に以下のみを与える。

* Aの該当source
* Bの該当source
* A→Bを生んだimport/call周辺
* 必要な最小限の前後文脈
* 既存経路表
* 既存機能一覧
* 関連する台帳記録
* runtime evidence

原則：

sourceを読ませる。ただし候補を理解するために必要なsourceだけを読ませる。

設計意図を創作させない。

---

## 9. Workerの判定反復

同一候補について複数回判定を取得してよい。

初期仕様では3回とする。

ただし、3票多数決を「真実の確定」とみなしてはならない。

同一モデル・同一入力から得られた複数票は独立した証拠ではない。

したがって票は、

Worker判定の再現性

として記録する。

例：

* vote 3/3：同一判定
* vote 2/1：不一致
* vote 1/1/1：不安定

割れた場合は原則として確定しない。

保存する項目：

* model
* prompt/version
* input hash
* 各票
* 最終分類
* 不一致回数

「安定している」等の散文のみで保存しない。

数値と実結果を保存する。

## 10. 段C：機能表の成長

### 10.1 基本方針

Function名は先に定義された一覧から選ぶ。

Worker自身にFunction名を創作させない。

### 10.2 新規機能候補

Workerが、

「一覧に無い」

または、

「在る物の中に近い物は無い」

を選んだ場合、新規Function候補として蓄積する。

この段階では正式Functionではない。

### 10.3 正式登録

新規Function候補は、既存の承認経路を使用して正式登録する。

新しい承認システムは作らない。

正式登録後にのみFunction一覧へ加える。

* OBSERVED_EDGE
* Worker votes
* Evidence

## 12. Workerの権限

Workerの権限は参照のみとする。

Workerは以下を行わない。

* git操作
* source変更
* 台帳への登記
* 経路表への直接追記
* Function一覧への直接追記
* 新規名称の自由生成

Workerは層1として必要情報を読む。

判断結果だけを返す。

## 13. Managerの役割

Managerは原則として以下だけを行う。

* front doorから問い合わせる

* Workerの判定結果を読む
* 必要な場合に既存の承認経路を使用する

Takaの操作回数を増やさない。

## 21. 想定される危険

### 21.1 /api/control の肥大化

問いを増やすほど取得時間が増える可能性がある。

対策：

要求された項目のみ計算する。

### 21.2 Workerの過剰肯定

LLMは「無い」よりも「在る」と判定しやすい場合がある。

対策：

必ず、

* 判断できない
* 一覧に無い
* 近いものは無い

を明示的選択肢として持つ。

票が割れた場合は採用しない。

### 21.3 候補爆発

389本のPython fileから大量Edgeが出る可能性がある。

対策：

段1で総数を確認する。

Worker接続前に機械的な分類・集計を行う。

候補が多すぎる場合は、

* runtime evidence
* repo跨ぎ
* callあり
* 送受信記録

等の決定論的属性で優先順位を付ける。

### 21.4 LLMへ過剰なsourceを渡す

repo全体を読ませると、Workerが再び探索者・設計者になってしまう。

対策：

候補を理解するための局所sourceだけを渡す。

## 22. 本システムが最終的に提供する問い合わせ

完成後、2DERは少なくとも以下へ回答できる。

**部品起点**

「この部品は何をするものか」

Component → Function

**機能起点**

「登記機能はどこにあるか」

Function → Component

**経路起点**

「submitからどこを通るか」

Component → ROUTE_EDGE → Component

**実績起点**

「この経路は本当に通ったことがあるか」

ROUTE_EDGE → OBSERVED_EDGE → Evidence

**欠落起点**

「コードでは繋がっているが経路表に無いものは何か」

STATIC_EDGE − Registered ROUTE_EDGE

**未稼働起点**

「経路として存在するが実行記録が無いものは何か」

ROUTE_EDGE − OBSERVED_EDGE

## 23. このシステムの位置づけ

本システムは「経路表自動生成システム」ではない。

経路表は出力の一つにすぎない。

実体は、

2DER内部の構造・機能・接続・稼働実績を、自己観測によって維持する内部モデル

である。

人体に例えるなら、

* Component = 心臓
* Function = 循環
* Edge / Route = 動脈・静脈
* Evidence = 実際の血流観測

に相当する。

部品図、機能表、経路図、稼働記録を別々に管理するのではなく、相互参照可能な一つの構造として扱う。

---

## 24. 設計上の保存則

本実装では以下を守る。

1. 機械に意味を判断させない。
2. LLMに存在を発明させない。
3. LLMにrepo全体を探索させない。
4. Workerに自由命名させない。
5. 不明を正式な状態として保持する。
6. 実行実績と静的構造を混同しない。
7. 同じ情報を人間に二度探させない。
8. Managerを探索者に戻さない。
9. 新しい台帳・入口・承認工程を安易に増やさない。
10. 各段階で実測して一度停止する。

## 26. 完了条件

本仕様の初期完成は、18区間すべてが完全に分類されることではない。

以下が成立した時点を初期完成とする。

1. コードから未登録接続候補を機械が自動生成できる。
2. Workerが候補1件を限定メニューで分類できる。
3. STATIC_EDGE / ROUTE_EDGE / OBSERVED_EDGEが区別されている。
4. Functionを既存一覧から分類できる。
5. 「一覧に無い」を新規候補として保持できる。
6. 承認されたFunctionが一覧へ追加される。
7. 経路表・機能表・実績をfront doorから取得できる。
8. ManagerおよびTakaがrepo探索を行わずに状態を確認できる。

この8条件が成立した後、対象範囲を拡大する。

---

## 結論

本システムの目的は経路表を完成させることではない。

2DER自身が、自分に何が存在し、何と何が繋がり、それぞれが何を担い、実際にどこが動いたのかを、自分自身の記録から継続的に再構成できる状態を作ることである。

そのため、

* 存在の発見は機械
* 意味の分類はWorker
* 実績の確定は実行記録
* 正式登録は既存管理系

へ責任を分離する。

経路表と機能表は、この自己モデルから生成される閲覧面として扱う。
