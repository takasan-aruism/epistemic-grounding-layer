## 1. ★作るもの（thin・1問だけ）

### 1-1. 新規モジュール `twoder/ledger_query.py`
**固定・列挙可能・read-only・LLM ゼロ・決定論。**

```python
_CATALOG = {
    "record_by_id": {...}   # ★これ1件だけ。他は入れない
}
```
- **`record_by_id`**: 台帳 ID を1つ受け取り、**その ID の記録を返す。**
- **カタログは辞書1個。増やすのは次の build。** **今回1件しか置かないことを、コードのコメントに書く。**

### 1-2. ★台帳の対応表は「コードから確認して作る」。推測で足さない
- ID 接頭辞（`DE` / `RREQ` / `RINT` / `RSIG` / `UTT` / `DEV` / `ADM` など）と、**どのファイルがその記録を持つか**の対応表を作る。
- **★各接頭辞について、その台帳を書いている本番コードを特定してから map に入れること。** **file:line を SPEC 準拠の報告に書く。**
- **コードから特定できなかった接頭辞は map に入れない。** **`NOT_ANSWERABLE` を返す。**
  **【未確認】** 私は `UTT-*` の記録先を確認していない（`ds/ds/phase0.py:19` に `LOG_NAME = "ds_events.jsonl"` が在ることまでしか見ていない）。**推測を SPEC に書かない。IMPL が事実で埋める。**
- **既存の登記が使えるなら使う。** `egl/structure/LEDGER_REGISTRY.jsonl`（全47台帳の登記簿）が在る。**使えるか確認し、使えるなら作り直さない。使えないなら理由を書く。**

### 1-3. ★★返る状態は3つ。潰さない
| 状態 | 意味 | 誤って潰すと |
|---|---|---|
| **`ANSWERED`** | カタログに問いが在り、ID が map に在り、**記録が見つかった** | — |
| **`NOT_FOUND`** | カタログに問いが在り、ID の接頭辞は map に在り、**探したが記録が無い**（探索条件を記録） | — |
| **`NOT_ANSWERABLE`** | **カタログに該当する問いが無い／接頭辞が map に無い＝機能が存在しない** | **★これを `NOT_FOUND` に潰すと「探して無かった」に化ける。無い機能が、無いデータに見える** |

**これは `rri/rri/existence_grounding.py` の既存規律と同型である**（逐語: 「`UNKNOWN` を `NOT_FOUND` に潰さない」「**『存在しない』と誤って言うことは、答えないことより有害である**」）。
**同じ考え方を使う。ただしコードは流用しない**（あちらは df 閾値つきの曖昧探索、こちらは ID の完全一致。**別物を無理に共有しない**）。

### 1-4. ★全件フォールバックを禁じる（MGR §3-3・本日の第一原則）
> **該当が無いとき、別のものを返してはならない。** **「無い」を返す。**
- **`runtime_inspection.build_request` の `requested = list(_CATALOG.keys())` と同じ書き方をしない。**
- **`information_need` に該当が無ければ、空でも全件でもなく `NOT_ANSWERABLE` を返す。**
- **★理由**: **黙って別のものを返すのは、無いものを在ることにする行為である。** Build 8 の食い違いはこれで起きた。

- **★これは私の予想である。実行して確かめること。** **壊れたら止めて設計へ上げる。勝手に assert を書き換えない。**
