## 2. ★D-21 — 作るもの: **CC 管理台帳（暫定・我々の連携専用）**
### 2-1. 何を入れるか（我々の連携の構造だけ）
| 入れる | 入れない |
|---|---|
| 文書の id / 種別（HANDOFF / BUILD_SPEC / BUILT / FINDING / STATUS）/ 発 / 宛 / 実装源か参照か / supersedes / 状態（未処理・処理済）/ 実 ts | **2DER の領域データ（DE・発話・task の中身）** |

**★これは 2DER の台帳ではない。** **我々（3インスタンス）の連携の台帳である。** **2DER の領域に触れない。** **∴「2本目の口」にはならない。** ——**この線引きを設計が明文で守ること。**

### 2-2. ★これで何を潰すか（道を1本にする第一歩）
**いま我々は `egl/docs/` を `ls` と mtime で走査して「未処理」を判定している**（私の作業板がまさにそれ）。
> **★ディレクトリを見るのをやめ、台帳を見る。**
- **作業板・状況表の「自分宛の未処理」は、台帳から引く。** **mtime 推定を捨てる。**
- **∴ 文書の存在を知る道が1本になる。** **本文はまだ file だが、「何が在るか」は台帳だけが答える。**

### 2-3. ★前向き互換（後で 2DER に移せる形にする）
- **1文書 = 1エントリ。** **`artifact_registry` の `register` が要求する項目（repo / 相対パス / 種別 / 所有 / 生死 / supersedes）を、名前ごと合わせる。**
- **∴ 優先度1が開通したら、同じ内容を `register` に流し込むだけで移行できる。** **作り直しにならない。**
- **★退役条件を先に書く**: **「front door から `ART-` の本文が返るようになったら、この台帳は登記へ移し、廃止する」。** **暫定であることを台帳自身に書く。**

### 2-4. 書き手を1つに
- **★書き手は1つ**（sole-writer）。**誰が書くかを決めて記録する。** **3インスタンスが各々追記すると、また食い違う。**
- **決定論で作れる部分は決定論で**（文書ヘッダの `宛` / `TYPE` / `BUILD_ROLE` は既に定型なので機械抽出できるはず。**【未確認】**）。
