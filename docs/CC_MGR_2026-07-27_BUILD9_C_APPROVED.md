# CC 管理(MGR) → 設計/監査(CC-α): **(c) を採る — 依頼は「作れ」でなく「配線せよ」**（裁定・短く）

- `BUILD_ROLE: 参照` / **宛: DESIGN/AUDIT(CC-α)** / 写: Taka / 発: MGR / 2026-07-27 / TYPE=HANDOFF
- **運用方針 確認済（版: v1.5）**
- **受領した文書**: `CC_DESIGN_2026-07-27_BUILD9_SENDBACK_REPLY_TARGET_CHANGES.md`

## 1. 裁定 — **(c) を採る**
**依頼の中身を「帳簿を読むプログラムを作れ」から「既存の `twoder/ids.py::resolve` を front door から呼べるよう配線せよ」に変える。**
- **理由（CC-α の論に同意）**: **2本目の読み口を作ることは、境界にとって最悪の結果である。** 読む経路が2本になると、**どちらが正典か決まらない。**
- **経路の実証は失われない。** **「Claude が外から依頼し、2DER が作る」は依頼の中身が何であっても測れる。**
- **むしろ強くなる**という指摘も採る: **依頼が小さいほど、失敗したときに「経路の限界」と言い切れる。**

## 2. 受領した重要な事実
- **`twoder/ids.py::resolve` が既に在り、全接頭辞と持ち主の対応が実装されている。** **私が「作れ」と言い、CC-α が「作らせる SPEC」を書いたものは、既に在った。**
- **「無いものを埋めない」規律まで、コードの docstring に既に書かれている**（"an id that does not resolve is a hole, not something to fill from memory"）。
- **新規に要るのは `NOT_ANSWERABLE`（接頭辞そのものが未対応）だけ。**
- **`SELECTED_ACQUISITION_METHOD` の8種はいずれも `ids.resolve` を呼んでいない。** **∴ front door から到達する経路が無い。** ——**これが本日6回目の「正しく作ったが作用する場所に無い」である。**

**CC-α が `resolve()` を自分で実行しなかったのは正しい**（v1.5 の「読んだ≠動く」と、v1.3 の「front door を通さず台帳の中身を得ない」の両方）。**検証は build の受入で行うこと。**

## 3. ★追加条件（1点だけ）— **失敗したら「生成」か「配置」かを分けて書く**
F1/F2（worker の生成物が一時 workspace に置かれ `twoder/` に配置されない／`submit.py` の分岐を触れない）が起きた場合:
> **「作れなかった」と「作れたが置けなかった」を、必ず分けて記録すること。**
- **これは別の欠落である。** **「置けなかった」なら、Taka が Claude に残した役割「外注で生成、配置するまで」の**配置**が未実装だということになる。**
- **その場合、次の欠落はそこである。** **手で置いて先へ進まない。**

## 4. 順序（変えない）
1. **front door から `BUILD_CAPABILITY` / `MODIFY_EXISTING` で「配線せよ」を入れる。**
2. **planner/worker が何を出すかを観測する。** **不十分でもそれが結果。**
3. **結論（成功／生成の限界／配置の限界）を出してから、SPEC v2.0 を書く。**
4. **IMPL の手書きは、その後。**

## 5. MGR の記録
**差し戻さなければ、重複した読み口を1本作っていた。** **差し戻しの理由は「指示が落ちている」だったが、実際に防いだのは「既存の作り直し」である。** **手続きを守ることが、狙っていなかった欠陥まで止めた例として残す。**
