### ★1-1. §3 の LIVE 検証が、実際に私の誤りを止めました【監査:IMPL】
私は当初 RETRIEVE の裏付けに **`retrieve`** を挙げましたが、`--check` が **RED** を出しました。
- **`EDGE_INVENTORY` で LIVE なのは `answer_question` だけ**で、`retrieve` は独立には LIVE ではありません（`answer_question` の内部からのみ到達）。
- 裏付けを **`answer_question` + `check`（両方 LIVE）** に訂正しました。
- ＝ **「できるつもり」を機械が止めた実例です。** negative control（LIVE でない symbol を混ぜると RED）も PASS。

### ★1-2. SPEC §3 の参考値との差異（feasibility-first）
SPEC §3 は 検索=**`acquire`** を挙げていますが、**`acquire` は外部 adapter（HTTP/GitHub）による取得**であり、SPEC §2 の RETRIEVE 定義「**既存 EGL に**問う」とは別物です（ネットワークにも出ます）。上記のとおり `answer_question` + `check` を使いました。**参考表の訂正をご検討ください。**

### ★1-3. 測定上の断り（隠しません）
注入試験の比較には `answer_question`（LLM を呼ぶ）ではなく、**その内部の決定論サブステップ `retrieve` を直接叩いています**。LLM を挟むと run 間ノイズ ≈0.10 が arm 間差に混入するためです。**`retrieve` 単独は LIVE ではありません。** LIVE 経路は `answer_question` 経由であり、測定のために内部段を叩いている、という事実を明記します。

## 2. ★★§4 注入試験（本体）【監査:IMPL】
**対照設計**: 同一 fixture・同一の「正しい戦略」から2アームを導出し、**下流だけを差し替え**ました。下流は完全決定論なので、**別 run どうしの比較ではありません**。

| 取り違え | n | routing が変わった | 片側だけ停止 | 両方停止 | 問いが同一 | 検索結果の重なり（Jaccard） |
|---|---|---|---|---|---|---|
| **遠隔**（DIRECT↔DEFER / DIRECT↔INTENT_PROBE） | 11 | **11/11** | **11/11** | 0 | 0 | — |
| **近縁**（CONTEXT_RESOLVE↔BMV / INTENT_PROBE↔PREMISE_PROBE） | 12 | **0/12** | 0 | 6 | 0 | **平均 0.036 / 最小 0.0** |

### 2-1. 遠隔の取り違え = **必ず routing ごと壊れる**【監査:IMPL】
11件すべてで **「動くか止まるか」が反転**しました。止まるべき時に動く、動くべき時に止まる。**これは問い合わせ規則に依存しない構造的な結果**です。

### 2-2. 近縁の取り違え = **routing は一切変わらないが、見に行く先がほぼ入れ替わる**
- `INTENT_PROBE`↔`PREMISE_PROBE`（6件）: **どちらも停止**。下流に到達しないので**下流は壊れません**（聞き返し文の文面だけが違う）。
- `CONTEXT_RESOLVE`↔`BMV`（6件）: **routing は同じ（両方アクション）なのに、検索で拾う記録の重なりが平均 3.6%**。最小 0.0（**完全に別物**）。
- ＝ **黙って別のものを見に行きます。** routing だけ見ていると気づけません。

### 2-3. ★★この近縁の数値には交絡があります（結論にしないでください）
**Jaccard 0.036 は、私が書いた `build_query` の副産物である可能性が高いです。**
- 私の実装では `CHOICE` → 問いに `選択肢 候補 比較` を、`BMV` → `観点 利点 欠点 評価` を**付け足します**。
- 検索は素朴なキーワード一致なので、**付け足した語が順位を支配します。**
- ＝ **「近縁の取り違えで下流の中身が激変する」は、意図調べの必要精度の話ではなく、私の問い合わせ規則の設計の話かもしれません。**
- **【設計:IMPL】** 別の（同じくらい妥当な）問い合わせ規則なら別の数字が出ます。**この数値を「0.71 で足りるか」の答えに使わないでください。**
- **確定できるのは遠隔側だけ**です（routing の反転は問い合わせ規則に依存しません）。

### 2-4. 現時点で言えること【設計:IMPL・断定しません】
> **遠隔の取り違えは必ず壊す。近縁の取り違えは routing を壊さない。**
> よって SPEC §4 が予告した「**必要なのは高い一致率ではなく遠隔の取り違えをしないこと**」の方向に、**遠隔側の証拠だけは揃いました。**
> ただし **近縁側は未決**です（§2-3 の交絡）。**「壊れた」の判定基準は私が作らず、材料だけを決定論で出しました**（SPEC §10(iii)）。
